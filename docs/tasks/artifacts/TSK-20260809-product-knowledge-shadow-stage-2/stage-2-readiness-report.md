## Итог

Реализация готовит выключенный по умолчанию теневой путь для одного
аутентифицированного Portal-разработчика и одной принадлежащей ему игры. Путь
выполняется после формирования ответа Editor, не меняет этот ответ и не пишет
в производственный либо Stage 1 Git. Модельный результат остаётся кандидатом в
изолированном PostgreSQL до будущего подтверждаемого контура.

Первый реальный пользовательский прогон выполнен 2026-08-11 после отдельного
решения PM: Cubica в этом контуре является pet-test, а не собственным
приложением или SaaS; Coding Plan разрешён только для этого теста, и
`abc → Antarctica` подтверждён как единственная связь разработчика и игры.
Прогон получил канонический `no_change`, не изменил основной ответ или Git и
был полностью очищен.

Первая последующая смысловая матрица выполнила три отрицательных вызова, но
остановилась на первом ожидаемом кандидате с безопасным `failed`; пятый вызов
не выполнялся. Terminal result и metric первых трёх были атомарно сохранены в
одноразовой PostgreSQL, но постоянная бесконтентная сводка из-за hard stop не
была дополнена до очистки. Поэтому матрица не доказала ни отрицательную
точность, ни полезность положительного пути. Prompt adapter усилен без
ослабления серверных проверок, однако реальная повторная оценка требует нового
явно разрешённого окна.

Историческое четвёртое окно с лимитом 25 секунд подтвердило отрицательную
матрицу и первый путь создания, но не коррекцию. Новое отдельно разрешённое
окно использовало 45 секунд только для себя, authority timeout 5 секунд,
lease 60 секунд и `maxAttempts=1` без retry. Оно сделало ровно четыре вызова:
три `no_change` (9272, 8640 и 3816 мс) и create proposal (26167 мс). Create
proposal нарушил правило «все и только подтверждённые факты», поскольку
выдумал/скопировал timestamp страницы, которого не было в trusted server input;
пятый correction не вызывался. Поэтому Stage 2 остаётся `in_progress`, а
Stage 3, чтение, применение и Git закрыты.

До provider call первая попытка остановилась на `message_changed`: PostgreSQL
`encode(bytea,'base64')` сворачивал длинный Base64. Байты и хэши были целы;
нормализация SQL-вывода добавлена во все claim/reread/prepare пути. Реальный
PG17 regression покрывает длинные user/agent messages, точный canonical
Base64 и 41/41 activation/security tests. Провайдер не вызывался (model
duration/input/output — ноль), затем cleanup обнулил состояние.

После окна gateway получил fail-closed trusted timestamp rule: точный ISO
`knowledge_timestamp` берётся из server clock в начале вызова, передаётся в
grounding и должен совпасть с parsed page timestamp; output не мутируется.
47/47 gateway tests, typecheck/generated types прошли, Luna-xhigh review —
`ACCEPT` без High/Medium. Постоянные timeout и retry остаются pending; 45s не
становится default.

После этого PM сохранил provider и модель, но перенёс синтез из ограниченного
web-процесса в устойчивое асинхронное задание. Критическое ядро готово: Editor
дожидается только авторизации Portal и долговечной записи очереди, а модель
вызывает отдельная one-shot worker-команда. Постоянный evaluator/runner также
реализован и локально принят: он наблюдает только уже поставленный штатным
Editor/Portal ход, передаёт worker точный owner/game/stable key и не создаёт
второй путь enqueue, queue, storage или service. Обычный scheduler остаётся
нетаргетированным.

Окно DR-13 выполнено 2026-08-23 после Sol-high preactivation `ACCEPT`. Три
отрицательных сценария дали `no_change` и прошли ручную рубрику 4/4. Первый
положительный сценарий завершился `gateway_malformed`; hard stop исключил
пятый вызов и любой retry. Всего выполнено четыре provider call. После
retention cleanup удалил 4 run, 4 metric, 8 сообщений и 4 thread: active
runs/metrics/messages/threads/text bytes равны нулю, Git неизменён, manifest
удалён. Окно не доказало положительные пути и не разрешает Stage 3.

DR-15 реализован 2026-08-24 без расширения публичного контракта. Adapter
классифицирует `gateway_malformed` одним из десяти закрытых бесконтентных
этапов; worker сохраняет его только в существующем `last_error_code`, а
evaluator показывает оператору до cleanup. Общий outcome, metric, постоянный
report, JSON Schema, generated types, миграции, retention и права не меняются.
Это устраняет необходимость в новой таблице, sidecar или диагностическом
сервисе. Новый внешний вызов по-прежнему закрыт.

## Реализованные границы

- Portal получает личность только из серверной аутентификации, проверяет право
  разработчика на игру и возвращает короткоживущую непереносимую HMAC-привязку.
- Editor пересылает Portal bearer только локальному AG-UI адресу с явно
  настроенным доверенным origin и серверной HMAC-аттестацией; внешний AG-UI его
  не получает.
- Enqueue-boundary использует только последнюю строковую реплику пользователя
  и ответ, действительно созданный серверным backend, а клиентскую историю и
  роли не считает источником истины. Ответ уже построен, но маршрут возвращает
  его только после ограниченной авторизации и долговечной записи задания.
- Отдельный worker имеет только право выполнять шесть фиксированных функций
  очереди. Он не хранит bearer и до и после модели заново проверяет Portal,
  точные сообщения, retention и полный набор policy bindings.
- PostgreSQL хранит точные байты, автора, порядок, ревизию, хэш, срок хранения,
  tombstone, один запуск на устойчивый ключ и бесконтентную метрику.
- Шлюз модели запрещён по умолчанию. Его test-only Z.AI Coding Plan adapter
  фиксирует endpoint и `glm-4.7`, ограничивает размер и время, передаёт полный
  разрешённый снимок wiki и проверяет JSON Schema, квитанцию авторизации,
  точные хэши, происхождение, страницу и разрешённую игру.
- Read-only основание открывает только серверно назначенный bare Git без
  методов записи, фильтрует Markdown-страницы существующей политикой роли и
  игры и точной ревизией доступа и заново строит временный `index.md` без
  названий запрещённых страниц. До чтения blob ограничиваются число исходных
  объектов, размер страницы и общий размер репозитория.
- Cleanup запускается одной ограниченной командой, вызывает только фиксированную
  SQL-функцию и выводит количества без текстов, ссылок и секретов.
- Истёкший или изменённый контент не передаётся модели; неизвестный результат
  оборванного вызова не повторяется автоматически.
- Постоянный evaluator запускается режимами `preflight`, `run-next`, `review`,
  `cleanup` через `npm run evaluate:shadow --workspace @cubica/product-context
  -- <mode>`. Он принимает только уже enqueue штатным Editor/Portal ход и
  передаёт worker exact owner/game/stable key; обычный scheduler не таргетируется.
  Пять категорий фиксированы и идут по порядку, worker делает одну попытку.
  Оператор заранее создаёт manifest, CLI его не создаёт: это owned regular JSON
  `0600` с exact `schema_version`, одним principal, единственным `applies_to`,
  ожидаемым HEAD и пятью фиксированными категориями с `stable_turn_key` в
  порядке. Пути задаются через `CUBICA_PRODUCT_CONTEXT_SHADOW_EVALUATION_MANIFEST`,
  `..._REPORT` и `..._WORKTREE`; manifest/report — разные абсолютные пути под
  `worktree/.tmp`, report может отсутствовать до preflight. Каталоги должны быть
  owned real directories без group/world write (`0700` рекомендуется). Реальные
  ID и тексты не публикуются. Report content-free и атомарен после каждого
  сценария. Raw material проверяется вручную через `/dev/tty`, в report остаются
  только булевы признаки.

## Изоляция и откат

Интеграция разрешена только из одного server-only модуля Editor. Проверка
репозитория запрещает новые зависимости и импорты `@cubica/product-context` из
остальных приложений, сервисов, игр и пакетов. При выключенном флаге hook не
создаётся. Ошибки авторизации, базы и модели поглощаются после построения
основного ответа.

Откат до активации состоит из выключения режима, отзыва model credential,
остановки вызовов cleanup и удаления отдельной shadow-базы. Производственный
канон, игровые сессии, редакторский Git и личная wiki при этом не меняются.

## Проверки

При реализации выключенного Stage 2 были подтверждены package acceptance,
PostgreSQL 17 integration с отдельным непривилегированным runtime-login,
Editor и Portal tests/build, единственная разрешённая интеграционная точка,
неизменность основного SSE-ответа, защита bearer и полный
`verify:canonical`. Три Sol high security review и две волны исправлений
закрыли все Critical/High/Medium замечания. Миграция отдельно прошла
statement-by-statement autocommit, проверку восстановления membership и
временных grants при искусственной ошибке.

После read-only grounding/cleanup были заново выполнены product-context
typecheck и тесты, Editor typecheck/build, shadow module tests, schema
generation, изоляция и независимый Sol high security review. После подключения
Z.AI отдельно прошли product-context typecheck, 69/69 целевых и 133/133 полного
unit-набора, Editor typecheck и 21/21 целевых тестов. Повторный Sol high review
принял исправления без Critical/High/Medium. Полный `verify:canonical` после
объединения изменений вновь подтвердил общие контракты, Runtime API, Player,
Editor и обе production-сборки.

Для постоянного evaluator отдельно подтверждены 17/17 evaluator tests,
включая crash/resume, удаление manifest после завершённого хода, hard stop,
атомарный `0600` report после каждого сценария, ручной `/dev/tty` review и
точную cleanup-проверку. Combined focused unit ранее прошёл 55/55 до добавления
этого теста. После security-remediation асинхронной границы PostgreSQL 17
прошёл 50/50 (40 activation/upgrade/security/race + 10 shadow postgres), а
целевой набор queue/evaluator/worker-config/Z.AI — 92/92;
независимый Sol high security re-review —
`ACCEPT`. Cleanup требует нулевые runs, metrics, messages, threads и text, а
Git остаётся неизменным.

Перед слиянием отдельно доказаны совместимость обновления уже применённых
`002` и ранней `003`, удаление устаревшей `worker_mark_calling`, точный набор из
шести worker-функций и отсутствие лишних `EXECUTE`. App и worker на каждой
транзакции проверяют отдельный непривилегированный login с единственным прямым
membership. Реальные конкурентные тесты закрывают ожидание блокировки дольше
аренды, tombstone и cleanup до внешнего вызова и после него, изоляцию точного
evaluator-target, атомарный enqueue и потерю подтверждения commit. Итоговый
независимый Sol high review не оставил замечаний High/Medium.
Полный package-шлюз `verify:product-context` после этих изменений прошёл
257/257 на отдельной PostgreSQL 17; тестовые БД и роли после прогона удалены.

Закрытая синтетическая activation rehearsal 2026-08-11 дополнительно
подтвердила:

- product-context typecheck;
- 10/10 целевых тестов на одноразовой PostgreSQL 17, включая отдельный
  `NOINHERIT` runtime-login без административных прав, подготовленное membership
  в `product_context_shadow_app`, forced RLS, точные политики, триггеры,
  привилегии и cleanup-функцию; отрицательные сценарии отклоняют лишнюю
  привилегию/владение, permissive RLS и неверную привязку триггера;
- отказ при удалённом PostgreSQL URL и при выходе пути из `.tmp/` через
  промежуточную символическую ссылку;
- фиксированные синтетические сообщения, локальный `no_change`, один модельный
  вызов при точном повторе, одну запись run/metric и неизменный Git HEAD;
- успешный CLI при заведомо нерабочем provider URL: `PKS_KEY` и provider
  configuration не читаются, сетевой gateway не создаётся;
- JSON-вывод без текстов, ссылок на principal/repository, URL базы и секретов.

Составной приёмочный скрипт с обязательным URL одноразовой базы также прошёл:
product-context 10/10, Portal authorization 11/11, Editor shadow/forwarding
21/21 и машинная проверка единственной разрешённой интеграционной точки. Без
URL базы скрипт завершается отказом до тестов, поэтому DB-путь нельзя незаметно
пропустить. Повторное независимое Sol high review завершилось `ACCEPT` без
оставшихся Critical/High/Medium замечаний.

Одноразовая база после проверки удалена. Даже успешный `no_change` доказывает
только закрытый локальный контур, ограничения доступа и повторяемость; он не
доказывает смысловое качество точечного патча на реальной wiki и не разрешает
реальный shadow.

Первое смысловое окно использовало пять заранее определённых категорий и
обязательный hard stop. Три первых вызова завершили coordinator и имели
terminal result + metric в одноразовой базе, однако evaluator не перенёс их
точные исходы в постоянный бесконтентный отчёт до следующего сценария.
Ожидаемое создание новой страницы завершилось отказом до сохранения кандидата;
оставшийся update не вызывался. Одноразовые база, runtime-login/roles,
сообщения, ключи, bearer, копия Portal-базы и bare Git удалены; исходная
Portal-база и канон не менялись.

Raw provider payload по границе безопасности не сохранялся, а временный
evaluator не дополнял постоянный бесконтентный отчёт после каждого сценария.
Поэтому после удаления disposable PostgreSQL исходы первых трёх вызовов
недоступны, а конкретную причину `failed` четвёртого нельзя считать
установленной. Sol high статический разбор нашёл
объективный test gap: prompt не описывал полный `create_file`
Markdown contract и реалистичное локальное обновление provenance. Исправление
добавило эти инструкции и положительные regression-тесты; JSON Schema,
нормализация, exact anchors и проверки итоговой страницы остались прежними.
После исправления прошли product-context typecheck, 41/41 целевых тестов,
проверка сгенерированных типов, реестр долга, карта структуры и
`git diff --check`; независимый Sol high review завершился `ACCEPT` без новых
замечаний.

Повторное явно разрешённое окно исправило наблюдаемость операторского процесса:
до первого вызова evaluator доказал атомарную запись, `fsync`, повторное чтение
и права `0600`, а после каждого вызова сохранил отдельный бесконтентный итог.
Первые два сценария дали ожидаемый `no_change` за 3990 и 3536 мс. Третий
завершился `gateway_timeout` на фиксированном лимите 15006 мс; поэтому его
смысловая классификация неизвестна, а два положительных сценария по hard-stop
правилу не запускались. Git остался неизменным, кандидаты не сохранялись.

После срока хранения cleanup удалил 3 run и 3 metric, обезличил 6 сообщений и
3 потока и подтвердил 0 активных текстовых байтов. Одноразовые Portal,
PostgreSQL database/login, HMAC/JWT, Portal-копия и bare Git удалены. Повторное
окно не доказало полную матрицу и не разрешает Stage 3. Один timeout сам по себе
не является доказательством неверного prompt или недостаточного лимита; новый
внешний прогон требует отдельного решения PM и полного повторения ворот.

Третье явно разрешённое окно сохранило прежний 15-секундный лимит и впервые
доказало всю отрицательную матрицу: три ожидаемых `no_change` за 8549, 3344 и
5244 мс. Первый положительный сценарий завершился `gateway_timeout` за 15011
мс; повтор и сценарий коррекции не выполнялись. Таким образом, отрицательная
классификация подтверждена, но положительные create/update пути всё ещё не
прошли реальную смысловую оценку.

Четыре бесконтентных результата были атомарно сохранены до очистки. Cleanup
удалил 4 run и 4 metric, обезличил 8 сообщений и 4 потока и подтвердил 0
активных текстовых байтов; весь одноразовый контур удалён, Git и исходная
Portal-база не менялись. Повторяемый timeout на точной 15-секундной границе
теперь допускает отдельное предложение увеличить лимит следующего окна, но не
автоматическое изменение: нужен новый PM gate, а prompt, JSON Schema и
серверные проверки ослаблять или подстраивать нельзя.

Четвёртое окно использовало одобренные только для него model timeout 25 секунд,
coordinator lease 40 секунд (`25 + 2 × 5 + 5`) и полный предел процесса 50
секунд. Локальный preflight подтвердил эти значения и отсутствие retry. Три
отрицательных сценария дали ожидаемые `no_change` за 3352, 9337 и 9168 мс;
первый положительный сценарий дал одноперационный `proposal` за 13481 мс и
прошёл независимую Sol high смысловую проверку. Сценарий коррекции завершился
`gateway_timeout` за 25015 мс, поэтому его смысловой исход неизвестен.

До первого внешнего вызова во временном evaluator был найден пропущенный
`await`; он не успел обратиться к provider, PostgreSQL или создать сценарный
артефакт. После исправления preflight и контур были подготовлены заново.
Cleanup затем потребовал два ограниченных прохода: временный evaluator сначала
передал batch limit `5`, не учтя десять сообщений. Штатная cleanup-функция не
менялась; после проверки причины второй проход завершил операцию. Суммарно
удалены 5 run и 5 metric, обезличены 10 сообщений и 5 потоков, осталось 0
активных текстовых байтов. Одноразовый контур полностью удалён; Git и исходная
Portal-база не менялись.

Разрешение на 25 секунд израсходовано. Результат доказывает отрицательную
классификацию и создание нового знания, но не коррекцию существующего. Новый
внешний прогон, иной provider или постоянный timeout требуют отдельного решения
PM; запускать только пятый сценарий, повышать лимит или подстраивать prompt
нельзя. Эти вопросы собраны в
[отдельном реестре решений для пересмотра](stage-2-decision-review.md).

## Текущее handoff-состояние — 2026-08-13

Persistent content-free report записывался после каждого сценария. Cleanup
удалил 4 runs и 4 metrics, tombstoned 8 messages и 4 threads; осталось 0
active runs/metrics/messages/threads/text bytes. Disposable PostgreSQL, Portal
