# Stage 2 product knowledge shadow: отчёт готовности

## Итог

Реализация готовит выключенный по умолчанию теневой путь для одного
аутентифицированного Portal-разработчика и одной принадлежащей ему игры. Путь
выполняется после формирования ответа Editor, не меняет этот ответ и не пишет
в производственный либо Stage 1 Git. Модельный результат остаётся кандидатом в
изолированном PostgreSQL до будущего подтверждаемого контура.

Первый реальный пользовательский прогон ещё не выполнен: для него нужны
непроизводственные Portal/Editor, совместимый Cubica model gateway, отдельные
credentials, разрешающая политика и эксплуатационное расписание очистки.

## Реализованные границы

- Portal получает личность только из серверной аутентификации, проверяет право
  разработчика на игру и возвращает короткоживущую непереносимую HMAC-привязку.
- Editor пересылает Portal bearer только локальному AG-UI адресу с явно
  настроенным доверенным origin и серверной HMAC-аттестацией; внешний AG-UI его
  не получает.
- Post-response hook использует только последнюю строковую реплику пользователя
  и ответ, действительно созданный серверным backend, а клиентскую историю и
  роли не считает источником истины.
- PostgreSQL хранит точные байты, автора, порядок, ревизию, хэш, срок хранения,
  tombstone, один запуск на устойчивый ключ и бесконтентную метрику.
- Шлюз модели запрещён по умолчанию, ограничивает URL, размер и время,
  проверяет JSON Schema, точный хэш, источники и разрешённую игру.
- Истёкший или изменённый контент не передаётся модели; неизвестный результат
  оборванного вызова не повторяется автоматически.

## Изоляция и откат

Интеграция разрешена только из одного server-only модуля Editor. Проверка
репозитория запрещает новые зависимости и импорты `@cubica/product-context` из
остальных приложений, сервисов, игр и пакетов. При выключенном флаге hook не
создаётся. Ошибки авторизации, базы и модели поглощаются после построения
основного ответа.

Откат до активации состоит из выключения режима, отзыва model credential,
остановки вызовов cleanup и удаления отдельной shadow-базы. Производственный
канон, игровые сессии, редакторский Git и личная wiki при этом не меняются.

## Проверки

На момент создания отчёта свежо подтверждены:

- Editor typecheck, production build и целевые route/module tests — 16/16;
- package schema generation, typecheck и полный acceptance — 92/92;
- PostgreSQL 17 integration — 8/8 с отдельным непривилегированным runtime
  login, принудительным RLS, атомарными terminal result + metric, точным
  восстановлением membership options и откатом временных grants при ошибке;
- Portal unit tests — 16/16 и успешная Strapi build;
- машинный контроль единственной разрешённой интеграционной точки;
- неизменность основного SSE-ответа при успехе, ошибке и timeout shadow;
- защита Portal bearer от подложенного Host/origin;
- полный `verify:canonical`, включая Runtime API, Player, Editor и production
  builds, завершён успешно;
- три независимых Sol high security review и две волны исправлений — финальный
  ACCEPT merge-ready для выключенного Stage 2, без Critical/High/Medium
  блокеров;
- миграция отдельно выполнена PostgreSQL 17 statement-by-statement в обычном
  autocommit-режиме, а не только одним составным запросом.

После финального remediation дополнительно подтверждены Editor 14/14, Portal
11/11, model gateway/coordinator 24/24 и полный пакет
`verify:product-context` 97/97 на одноразовом PostgreSQL 17. Проверка миграции
включает два autocommit-прогона, прежний membership с `SET FALSE` и искусственную
ошибку внутри атомарного блока без оставшихся расширенных прав. Strapi
production build также завершён успешно.
Финальный `verify:canonical`, запущенный после всех исправлений, подтвердил
общие контракты, Runtime API, Player, Editor и обе production-сборки.

Реальный model gateway не проверяется без endpoint, credentials и разрешённой
политики.

Текущий запрос gateway передаёт точный ход и разрешённую игру, но не содержимое
существующей wiki. Совместимый gateway должен получить read-only основание
самостоятельно и вернуть точечный патч с проверяемыми источниками либо
`no_change`. Иначе можно оценить безопасность транспорта и извлечение нового
кандидата, но нельзя честно оценить качество изменения существующего знания.

## Остаточные условия активации

До передачи настоящих диалогов необходимо:

1. создать отдельную базу и непривилегированный runtime-login с явным
   membership в `product_context_shadow_app`;
2. использовать loopback либо PostgreSQL TLS с `sslmode=verify-full`;
3. настроить test/staging Portal и Editor, доверенный origin и разные HMAC-ключи;
4. предоставить совместимый gateway URL, credential и ревизию разрешающей
   политики внешней обработки;
5. запускать бесконтентную очистку чаще минимального срока хранения;
6. выбрать одного разработчика и одну игру, затем заранее согласовать сам
   реальный прогон и его ограниченный объём.

Model gateway сохраняет значение timeout по умолчанию `15s`. Верхнее значение
`45s` нельзя использовать с текущим `maxDuration=60`: две повторные Portal
authorization по 5 секунд и финальная запись должны иметь отдельный запас.
