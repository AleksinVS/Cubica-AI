# Спорные исполнительские решения ИИ-разбора CMT

## DEC-DEBRIEF-001: отдельный read-only путь вместо Agent Turn

- **Решение:** генерация не является Game Intent и не использует Agent Turn.
- **Почему:** Agent Turn может выбрать мутационное действие, а производный
  разбор не должен иметь такой возможности.
- **Пересмотреть, если:** появится общий контракт read-only assistant jobs,
  физически отделённый от выбора и исполнения Game Intent.

## DEC-DEBRIEF-002: синхронный ограниченный вызов без worker

- **Решение:** первый явный запуск ждёт один ограниченный provider call; ошибок
  автоматически не повторяет.
- **Почему:** один черновик одной сессии пока не оправдывает очередь, lease,
  scheduler и отдельный процесс. Обычные итоги остаются доступными при timeout.
- **Пересмотреть, если:** измеренный p95 не помещается в HTTP-бюджет либо
  одновременно запускается достаточно разборов для контролируемой очереди.

## DEC-DEBRIEF-003: одна таблица попыток, один successful draft

- **Решение:** каждая попытка является session-owned записью, а частичные
  уникальные ограничения допускают только одну активную попытку и один
  успешный черновик на сессию.
- **Почему:** так сохраняются ошибки и ручные повторы без второй таблицы или
  потери аудита; удаление сессии естественно каскадирует данные.
- **Пересмотреть, если:** появится редактор версий, утверждение/публикация или
  несколько разных видов отчёта одной сессии.

## DEC-DEBRIEF-004: thinking отключён

- **Решение:** Z.AI вызывается с отключённым thinking и JSON mode.
- **Почему:** продукту нужен проверяемый структурированный результат, а не
  отдельный корпус внутреннего рассуждения с неясным хранением и приватностью.
- **Пересмотреть, если:** измеряемая оценка качества докажет необходимость
  thinking и будет принята политика его передачи и аудита.

## DEC-DEBRIEF-005: стабильный React UI вместо Cubica Surface

- **Решение:** schema-backed draft рисует обычный общий компонент; модель не
  генерирует UI surface.
- **Почему:** структура экрана известна заранее, поэтому Surface добавил бы
  ещё один валидируемый контракт без новой пользовательской возможности.
- **Пересмотреть, если:** несколько помощников потребуют динамически
  компонуемые facilitator surfaces из принятого каталога.

## DEC-DEBRIEF-006: API допускает явный запуск на закреплённой границе, CMT UI — только после финала

- **Решение:** сервер требует facilitator credential и точную версию снимка,
  а CMT показывает кнопку только в `finished`. Общий Runtime не содержит
  предметной проверки CMT phase.
- **Почему:** перенос завершённости каждой игры в общий Runtime создал бы
  game-specific ветку или преждевременный DSL. Ведущий является доверенным
  владельцем момента анализа, а точная граница сохраняется в аудите.
- **Пересмотреть, если:** второй потребитель потребует общего декларативного
  условия доступности assistant jobs.

## DEC-DEBRIEF-007: provider adapter пока не извлекается в общий пакет

- **Решение:** минимальный adapter живёт в модуле debrief Runtime API и не
  зависит от product-context shadow gateway.
- **Почему:** два потребителя используют разные endpoint profiles, входы,
  результаты и failure semantics; общий framework сейчас увеличит связанность.
- **Пересмотреть, если:** третий production-потребитель повторит измеримый
  общий transport/error/audit профиль.

## DEC-DEBRIEF-008: жёсткие границы одного provider call

- **Решение:** один вызов ограничен 45 секундами, 2 MiB сериализованного
  запроса, 512 KiB ответа и 4096 output tokens; превышение не повторяется
  автоматически и сохраняется как неуспешная попытка.
- **Почему:** переносимый журнал допускает до 32 MiB, но отправка такого объёма
  в синхронный внешний вызов не помещается в безопасный HTTP- и стоимостной
  бюджет первого среза. Обычный журнал и итоги игры при этом остаются доступны.
- **Пересмотреть, если:** измерения реальных CMT-сессий покажут недостаточность
  лимита либо появится принятая асинхронная стратегия сегментации/суммаризации.

## DEC-DEBRIEF-009: явное восстановление зависшей попытки через два таймаута

- **Решение:** статус `generating` не запускает автоматический повтор. Если он
  старше 90 секунд — двух предельных 45-секундных вызовов — следующий явный
  POST ведущего атомарно помечает прежнюю попытку `internal_error` и создаёт
  новую. Поздний результат прежнего `runId` уже не может записать черновик.
- **Почему:** падение процесса между durable begin и completion иначе навсегда
  блокировало бы единственный черновик. Отдельный lease-worker для одного
  синхронного документа был бы необоснованным усложнением.
- **Пересмотреть, если:** появится очередь фоновых заданий, измеренный provider
  timeout изменится или несколько runtime-процессов потребуют heartbeat/lease.
