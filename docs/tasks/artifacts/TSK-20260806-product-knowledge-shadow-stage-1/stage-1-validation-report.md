## 1. Итог этапа

Stage 1 реализует изолированное серверное ядро продуктовых знаний и не
подключает его к действующим помощникам Cubica. Проверка доказывает форму
контрактов, локальность Markdown-правки, ролевую выдачу, жизненный цикл
операции PostgreSQL и согласование с управляемым Git на синтетических данных.

Этот результат не разрешает промышленное чтение или запись. Следующим может
быть только отдельный непроизводственный теневой этап после выполнения
условий раздела [7](#7-готовность-к-миграции).

## 2. Исходная база и изоляция

- Работа начата от актуального `main` на commit `f734ebae` в отдельном чистом
  worktree.
- Ранее известный красный сценарий полной макетной партии уже исправлен в
  `main`: целевой тест и полный набор `runtime-api` прошли до начала Stage 1.
- В проекте по-прежнему нет единой промышленной личности, общего
  `ConversationStore` (хранилища точных диалогов) и единого шлюза Cubica к
  языковой модели. Их тестовые замены не объявлены промышленными контрактами.
- Новый пакет не является сервисом и не импортируется приложениями, играми
  или рабочими сервисами. Автоматическая проверка запрещает production-
  зависимость, импорт, маршрут, инструмент или переменную запуска стенда вне
  изолированного контура.
- Синтетический `ConversationStore` хранит в памяти процесса только точные
  байты, ревизию и автора тестового сообщения. Третья продуктовая таблица для
  него не создаётся.
- Текущий полный `index.md` хранится в закрытом Git, а роль получает только
  временную отфильтрованную проекцию без названий запрещённых страниц.

## 3. Угрозы и отказы

Проверенные границы безопасности:

- JSON Schema остаётся единственным структурным источником истины; типы
  генерируются, а строгий валидатор выполняет схему в рантайме.
- Неизвестная роль, предметная ссылка или политика запрещает операцию по
  умолчанию.
- Подтверждение привязано к точной паре `operation_id + patch_hash`;
  содержательный payload и единый конверт оснований после создания
  неизменяемы.
- PostgreSQL использует принудительную строковую изоляцию (RLS — правила,
  скрывающие чужие строки), отдельную не владеющую таблицами роль и
  транзакционно локальную личность. Возвращённое в пул соединение не сохраняет
  личность предыдущего пользователя.
- Готовая операция захватывается короткой арендой через `SKIP LOCKED`; Git не
  выполняется внутри SQL-транзакции.
- Git вызывается без shell, hooks и filters, с закрытой средой, фиксированными
  аргументами и удерживаемым файловым дескриптором каталога. Модель не может
  выбрать `index.md`, служебный путь или произвольную Git-команду.
- До выдачи знания, сохранения предложения и Git-коммита повторно проверяются
  личность, роль, применимость, версии политик, точные источники, результат
  проверки влияния и базовый commit.
- Автоматическое применение решает сервер по точным уже разрешённым
  сообщениям. Клиент не может прислать флаги «точная команда» или
  «однозначно», а подтверждающий текст должен побайтово совпасть с репликой
  пользователя.
- Смысловой обзор вызывается сервером и возвращает квитанцию, привязанную к
  `operation_id`, точному патчу и отпечатку влияния. Произвольное либо повторно
  использованное `no_issue` не разрешает Git-коммит.
- `cubica_id` — устойчивый идентификатор страницы — неизменяем для
  существующей страницы и уникален во всём доверенном дереве. Дубликат
  запрещается до обзора, а не оставляется на усмотрение модели.
- Секретоподобный текст блокируется до появления операции PostgreSQL.
- Порт смыслового обзора не подменяется фиктивным ответом: если текущая
  детерминированная проверка требует обзора, отсутствие результата переводит
  операцию в явный конфликт `requires_extended_review`.

## 4. Качество и пользовательские сценарии

Синтетический набор использует одну личность, две роли и две игры в одной
личной области без копий по роли или игре. Он проверяет:

- точную команду «запомни» с одним Git-коммитом;
- неоднозначное предложение без изменения Git до точного подтверждения;
- чтение в следующем ходе;
- локальное исправление без изменения соседних байтов и страниц;
- логическое забывание;
- отсутствие утечки developer-знания роли facilitator через оглавление,
  прямой идентификатор, ссылку, буквальный поиск или текст ошибки;
- явно подтверждённое `global` и `all-user-games` для обеих ролей и двух игр;
- конфликт при изменении прав, политики, сообщения, результата проверки
  влияния или базового Git commit.
- исключение производной страницы из всех путей чтения, если точный хэш её
  основания больше не совпадает;
- запрет полного переписывания существующей страницы через комбинацию
  удаления и повторного создания того же пути.

Этап не оценивает качество извлечения смысла из живых разговоров: языковая
модель и сеть намеренно отсутствуют. Поэтому корректность хранения доказана,
а полнота и полезность реального синтеза ещё нет.

## 5. Забывание, стирание и восстановление

- Удаление синтетического сообщения оставляет бесконтентную отметку источника.
  Уже отдельно подтверждённое знание остаётся, а новая операция со старой
  ревизией не применяется.
- Логическое забывание удаляет страницу из текущего дерева, полного
  `index.md`, обычной ролевой выдачи и временного SQL-payload, но сохраняет
  закрытую Git-историю.
- Тест физического стирания удаляет ссылку и журналы одноразового репозитория,
  запускает Git GC и проверяет отсутствие контрольного текста среди объектов.
  Это доказывает только локальный алгоритм, не KMS, производственные кэши или
  резервные копии.
- Разрыв после переключения Git-ссылки и до SQL-квитанции восстанавливается по
  точным `operation_id + patch_hash`: повтор завершает исходную операцию и не
  создаёт второй смысловой коммит.
- Очистка временного SQL-payload выполняется перед сверкой незавершённых
  Git-квитанций и повторно после неё. Поэтому отказ Git не удерживает уже
  применённые данные, а восстановленная строка очищается в том же цикле.
- SQL-триггер и JSON Schema одинаково требуют бесконтентное состояние для
  отклонённых и просроченных операций; прямой SQL не может оставить скрытый
  payload в терминальной строке.

## 6. Выполненные проверки

После последнего изменения поведения получены следующие свежие результаты:

- `npm run generate:types:check --workspace @cubica/product-context` и
  `npm run typecheck --workspace @cubica/product-context` — успешно;
- сфокусированный модульный набор контрактов, политики, Markdown, Git, ядра и
  PostgreSQL — 44 из 44 сценариев успешно;
- последовательный набор на отдельной PostgreSQL 17 и временном bare Git —
  21 из 21 интеграционного сценария успешно, включая конкуренцию, RLS,
  восстановление и сбой Git во время очистки;
- `npm run verify:product-context-isolation` — ноль production-зависимостей,
  импортов, маршрутов, инструментов и служебных маркеров; проверка закрывает
  также прямой относительный импорт и локальную `file:`-зависимость;
- независимый аудит безопасности уровня Sol/high завершён без блокирующих
  дефектов;
- `git diff --check` — успешно.

Первый чистый канонический прогон дополнительно обнаружил существующую ошибку
типа `player-web`, которую маскировал инкрементальный кэш: React-ref был
объявлен непустым, хотя до монтирования законно содержит `null`. Контракт хука
синхронизирован с фактической проверкой `current === null`; поведение
приложения не менялось. Следующий прогон прошёл 263 теста и production-сборку
игрока, затем обнаружил две ссылки редактора на удалённое глобальное
пространство имён `JSX`. Они заменены на актуальный `React.JSX`; это также
только совместимость типов без изменения поведения. Сфокусированные
typecheck и production-сборка редактора прошли; тем самым все составные части
канонического шлюза имеют свежий зелёный результат.

Итоговые дополнительные доказательства:

- полный `npm run verify:product-context` — 65 из 65 сценариев успешно;
- ручной `npm run run:product-context-stage1 -- --synthetic-only
  --deny-external-processing` — запоминание, исправление и забывание успешны,
  создано ровно три смысловых коммита;
- `node scripts/dev/generate-structure.js --check` — карта структуры
  соответствует описанным каталогам;
- повторный канонический прогон заново прошёл общие проверки, 341 выполненный
  тест и smoke `runtime-api`, 263 теста и production-сборку игрока, 6 тестов
  протокола и 192 теста editor-engine. Последняя изменённая граница отдельно
  завершена зелёными typecheck и production-сборкой редактора. Неизменённые
  дорогие части после этого не запускались третий раз.

Актуальные практики сверены через Context7 с документацией
[PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html),
[node-postgres transactions](https://node-postgres.com/features/transactions)
и [Git update-ref](https://git-scm.com/docs/git-update-ref).

## 7. Готовность к миграции

Stage 1 может рекомендовать подготовку отдельного непроизводственного
теневого этапа, но не активное включение. До миграции обязательны:

1. единая серверная личность и промышленная проверка ролей для редактора,
   Portal и ведущего;
2. промышленный `ConversationStore` с удалением и сроками хранения;
3. единый шлюз Cubica к разрешённой языковой модели и политика внешней
   обработки для каждой области;
4. пользовательский интерфейс различия, подтверждения, истории, забывания и
   запроса стирания;
5. сквозное физическое стирание с ключами, кэшами, экспортами и резервными
   копиями, а также опубликованные численные сроки;
6. обезличенный оценочный набор реальных диалогов и измеримое качество
   синтеза;
7. наблюдаемость, ограничение нагрузки, выключатель и проверенный откат;
8. отдельная задача миграции и прямое подтверждение PM.

Текущий вердикт: архитектурных или реализационных блокеров для подготовки
такого shadow-плана нет, но ни один перечисленный шлюз нельзя считать
выполненным только на основании синтетического Stage 1.

## 8. Остаточные риски

- Совместная обработка источников с несовместимыми политиками остаётся
  зарегистрированным legacy-разрывом и запрещает такой промышленный случай.
- Действующее значение `global` пока ограничено двумя известными ролями;
  поведение при добавлении новой роли требует отдельного решения.
- Удержание каталога через `/proc/self/fd` является Linux-реализацией; иной
  серверной платформе потребуется эквивалентный безопасный адаптер.
- Одноразовая очистка Git не доказывает удаление из производственных резервных
  копий или у внешнего поставщика.
- Уже показанный потоковый фрагмент нельзя отозвать; отзыв права блокирует
  только дальнейшую выдачу, инструменты и долговременную запись.
- Стенд не имеет транспортной границы запросов. Он доказывает повторяемость
  стабильного ключа и максимум один смысловой Git-коммит, но не обещает
  обработку повторной отправки запроса до получения `operation_id`. До shadow
  серверный API обязан назначать устойчивый ключ повторяемости запросу.
- Статическая проверка изоляции не пытается распознавать намеренно
  вычисляемые динамические импорты. Для Stage 1 это не блокер, потому что пакет
  не подключён к production и канонический контроль запрещает саму
  интеграцию; миграционная задача должна заменить этот запрет явным
  разрешённым адаптером.
