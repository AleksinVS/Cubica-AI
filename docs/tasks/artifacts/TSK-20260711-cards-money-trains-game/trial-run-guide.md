# Руководство пробной партии «Карты, деньги, поезда»

Это инструкция для PM и ведущего реальной пробной партии. Основной путь —
нормативная игра `cards-money-trains`: её манифест имеет `runtimeReady: true`,
а `runtimeBlockers` отсутствует. Пробный запуск проводит человек; инструменты
подготавливают окружение и фиксируют результат, но не играют партию за людей.

Mock-пакет (`cards-money-trains-mock`) оставлен только необязательным
регрессионным стендом. Он не является заменой нормативной партии и не должен
использоваться для продуктового вывода о готовности.

## 1. Цель и роли

Ведущий управляет одной общей сессией, проговаривает правила и подтверждает
действия команд. Участники сообщают решения устно, а ведущий вносит их через
доступные формы. PM наблюдает и заполняет отчёт, не записывая имена, личные
данные или психологические оценки.

Проверяется полный путь: настройка команд → старт → явный пропуск новости
первого хода и обслуживание → рынок и грузы → состав и движение → доставка и
расчёты → строительство → методическая пауза → финал и два зачёта.

## 2. Предварительная проверка

Откройте терминал в корне репозитория и проверьте инструменты:

```bash
node --version
docker version
skills/C_low-memory-host-operations/scripts/preflight.sh
```

Нужен Node.js не ниже `22.7.0`, работающий Docker и успешная проверка ресурсов
хоста. Не останавливайте неизвестные процессы ради освобождения памяти или
портов. Перед партией ведущий и PM также сверяют:

- исходный манифест содержит `config.runtimeReady: true` и не содержит ключа
  `config.runtimeBlockers`;
- открытый пакет — `cards-money-trains`, а не mock; на экране нет маркировки
  `MOCK` и точек `A–F`;
- PM подготовил пустой
  [шаблон отчёта](./trial-run-report-template.md) и назначил номер партии
  без персональных данных.

Если readiness или содержимое не совпадают, партию не начинать: зафиксировать
`block` в отчёте и передать проблему владельцу пакета.

## 3. Запуск нормативной игры

### PostgreSQL

При первом запуске создайте постоянный том и локальный контейнер PostgreSQL:

```bash
docker volume create cubica-cmt-pgdata
docker run -d \
  --name cubica-cmt-postgres \
  -e POSTGRES_USER=cubica \
  -e POSTGRES_PASSWORD=cubica_local_only \
  -e POSTGRES_DB=cubica \
  -p 127.0.0.1:55432:5432 \
  --mount type=volume,src=cubica-cmt-pgdata,dst=/var/lib/postgresql/data \
  --health-cmd "pg_isready -U cubica -d cubica" \
  --health-interval 2s \
  --health-timeout 5s \
  --health-retries 20 \
  postgres:17
```

Если контейнер уже существует, используйте `docker start
cubica-cmt-postgres`, а не повторный `docker run`. Дождитесь ответа `healthy`:

```bash
docker inspect --format '{{.State.Health.Status}}' cubica-cmt-postgres
```

### Runtime API

В первом отдельном терминале примените миграцию и запустите сервер правил с
постоянным хранилищем:

```bash
export SESSION_STORE=postgresql
export DATABASE_URL='postgresql://cubica:cubica_local_only@127.0.0.1:55432/cubica'
export PORT=3001
npm run migrate:sessions --workspace @cubica/runtime-api
npm run dev --workspace @cubica/runtime-api
```

Проверьте процесс, хранилище и готовность именно нормативной игры:

```bash
curl -fsS http://127.0.0.1:3001/health
curl -fsS http://127.0.0.1:3001/readiness
curl -fsS http://127.0.0.1:3001/games/cards-money-trains/readiness
curl -fsS http://127.0.0.1:3001/games/cards-money-trains/player-content
```

Любой неуспешный запрос означает `block`: не подменяйте PostgreSQL временным
`in-memory` ради продолжения партии.

### Player Web

Во втором отдельном терминале запустите общий экран ведущего:

```bash
RUNTIME_API_URL=http://127.0.0.1:3001 \
PORT=3000 \
NEXT_IGNORE_INCORRECT_LOCKFILE=1 \
npm run dev --workspace @cubica/player-web
```

Для обычной сессии откройте:

```text
http://127.0.0.1:3000/?gameId=cards-money-trains
```

После загрузки убедитесь, что видны нормативные терминалы `1–23`, `π` и `9¾`,
начальная сеть и реальные панели ведущего. Не используйте технический replay
для замены действий человека.

Изолированный helper предпросмотра нужен только для разработки или отдельной
визуальной сверки. Подготовка без регистрации не требует запущенных сервисов:

```bash
node games/cards-money-trains/tools/prepare-local-preview.mjs --no-register
```

Для регистрации источника уже запустите Runtime API и вызовите helper без
`--no-register`, указав адрес сервера. Helper принимает только готовый
манифест, копирует его без изменения readiness/blockers и не снимает
ограничения с исходного файла.

## 4. Новый сеанс и возобновление

### Новый сеанс

1. Для гарантированно новой локальной сессии откройте нормативный URL в
   отдельном временном профиле браузера без прежних данных сайта. Новая вкладка
   обычного профиля не подходит: она разделяет `localStorage` и возобновит
   старую сессию.
2. Если нужен новый сеанс в текущем профиле, сначала сохраните прежний
   идентификатор, затем в консоли разработчика выполните
   `localStorage.removeItem("cubica-cards-money-trains-session-id")` и
   обновите страницу. Это удаляет только локальную привязку; серверная запись
   прежней партии остаётся в PostgreSQL.
3. Запишите новый технический идентификатор из ключа
   `cubica-cards-money-trains-session-id` в отчёт; не записывайте имена людей
   или другие персональные данные. Убедитесь, что он отличается от прежнего.
4. Создайте от 4 до 12 команд в допустимом составе, назначьте контрастные
   обезличенные названия вроде «Команда 1» и подтвердите старт.
5. Сверьте стартовые деньги, технику, станции и порядок хода с экраном.

### Возобновление

Запустите PostgreSQL и оба сервиса теми же командами, затем откройте тот же
нормативный URL в том же браузерном профиле. Player Web прочитает ключ
`cubica-cards-money-trains-session-id`. Убедитесь, что идентификатор, фаза,
версия состояния, балансы, техника и доступные действия совпали с последней
контрольной точкой.
Если сессия не восстанавливается, не создавайте новую вместо неё: внесите
ожидаемое и фактическое в отчёт и остановите партию по разделу 6.

## 5. Сценарий полного цикла

Ведущий проходит пункты последовательно и отмечает время каждого перехода:

1. Настройка: создать команды и завершить подготовку; проверить стартовые
   деньги и размещение техники.
2. Первый ход: выполнить явное действие «Пропустить новость первого хода» без
   открытия или расходования карты, затем пройти обязательное обслуживание.
   Проверить отказ действия при недостаточном балансе, если он возникает в
   фактическом сценарии.
3. Рынок и груз: выполнить покупку допустимой единицы, завершить рынок,
   открыть грузовые предложения, выбрать одну физическую карту, погрузить её
   в подходящий вагон и сформировать состав до перехода к движению. Проверить,
   что невыбранная карта вернулась в свою колоду.
4. Движение и расчёты: подготовить порядок локомотивов, выбрать доступную
   дорогу, переместить уже сформированный состав и явно завершить движение
   текущего локомотива. Выполнить доставку/расчёт и сверить публичные балансы,
   тариф и статус груза.
5. Строительство: рассчитать и подтвердить одну дорогу или полустанок, затем
   проверить стоимость и геометрию. Обычный объект, построенный в ходу `N`,
   должен оставаться закрытым весь `N+1` и открыться в начале `N+2`; если
   пробная партия не доходит до этой точки, пометить проверку как непройденную,
   а не ставить `pass`. Не обходить форму прямыми запросами.
6. Восстановление: обновить страницу между фазами и повторно сверить
   состояние; при необходимости пройти явное возобновление из раздела 4.
7. Методика и финал: продолжить реальные ходы до доступной методической паузы
   (ориентиры после ходов 3 и 5), провести, перенести либо завершить её через
   интерфейс. На безопасной границе полного раунда запросить завершение,
   проверить отмену запроса, затем подтвердить финал. Сверить итоговую формулу,
   стоимость техники, долги и два отдельных зачёта.

Один цикл не заменяет наблюдение за несколькими командами: если время или
ресурсы ограничены, PM отмечает фактически пройденные пункты и не объявляет
непроверенные фазы успешными.

## 6. Безопасная остановка

Сначала сохраните контрольную точку и заполните текущие поля отчёта. Закройте
вкладку Player Web, затем остановите Player Web и Runtime API штатным
`Ctrl+C`, после чего выполните `docker stop cubica-cmt-postgres`. Не удаляйте
контейнер, том базы или `.tmp/editor-worktrees`, пока PM не сохранил
доказательства и не согласовал очистку. При аварии запишите
последнюю фазу и версию состояния, после чего возобновляйте только по разделу
4.

## 7. Критерии pass/fail

`pass` ставится, если полный сценарий пройден через обычные формы, каждая
контрольная точка совпала с ожидаемым состоянием, обновление/возобновление не
потеряли прогресс, а финал показал оба зачёта и формулу результата.

`fix` ставится при воспроизводимом дефекте, который не блокирует сохранность
сессии, но нарушает ожидаемое действие, читаемость карты/формы или методику.

`block` ставится, если readiness-проверка не проходит, нормативная игра не
стартует, действие меняет состояние неверно, восстановление теряет прогресс,
невозможно безопасно остановить сессию или нельзя подтвердить результат.

Каждая проблема записывается как «ожидаемое → фактическое → шаги
воспроизведения → серьёзность → доказательство»; скриншот, лог или номер
состояния хранится только в `.tmp/` и связывается с записью отчёта.

## 8. Отчёт и необязательная регрессия

Результат заполняется в [шаблоне отчёта](./trial-run-report-template.md): дата,
версия, устройство, размеры экрана, число команд, контрольные точки, проблемы,
читаемость, восстановление, методические паузы и итог `go/fix/block`.

После нормативной партии можно отдельно открыть
`?gameId=cards-money-trains-mock` и выполнить короткий регрессионный цикл. В
отчёте пометьте его как `optional regression`; его результат не меняет итог
нормативной партии и не доказывает готовность реального содержимого.

## 9. Ограничения

Локальный helper и технические replay не создают человеческих команд, не
имитируют решения участников и не заменяют сохранённый журнал. Не публикуйте
в отчёте имена, контактные данные, свободные психологические характеристики
или иные сведения, не нужные для воспроизведения технического результата.
