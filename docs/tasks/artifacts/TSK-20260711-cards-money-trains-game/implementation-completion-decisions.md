# Спорные решения доведения игры до полной реализации

## Статус и назначение

Документ хранит решения, которые основной агент принимает автономно при
доведении игры «Карты, деньги, поезда» до готового пользовательского пути по
прямому поручению PM от 2026-08-11. Они не являются новыми ADR и не меняют
принятые публичные контракты. Любое решение можно отдельно пересмотреть без
поиска по журналам исполнения.

Новая граница доверия, безопасности, хранения, совместимости или публичного
контракта сюда как принятая не записывается: она останавливает автономную
работу и выносится PM как архитектурный блокер.

## Исполнительские волны

| Волна | Результат | Исполнитель и цена ошибки | Приёмка |
| --- | --- | --- | --- |
| W1 | Независимо сходящиеся генераторы, актуальные случайностные тесты и cargo-фикстуры | `builder_complex`, Sol high: состояние и тестовая семантика имеют высокую цену тихой ошибки | повторная композиция, focused runtime tests и изолированная компиляция CMT |
| W2 | Точная карта незакрытых UI и методических действий | `scout`, Luna low: только ограниченный сбор доказательств | файлы, символы, реальные долги и пакет реализации без архитектурных решений |
| W3 | Полный обычный путь ведущего через UI без прямых API-команд | `builder`, Terra medium: обычная реализация после фиксированного пакета | unit/integration и нормативный browser replay всех фаз |
| W4 | Синхронные authoring, runtime blockers, GSR, TSK, checklist и долговой реестр | основной агент; документация и источник истины не делегируются разрозненно | isolated compile, schema checks и отсутствие противоречий |
| W5 | Финальная последовательная приёмка и решение о `runtimeReady` | основной агент; окончательная ответственность не делегируется | runtime, player, production build, browser E2E и свежий diff review |

Проверка на упрощение: новые сервисы, публичные операции, форматы хранения и
параллельный план не создаются. Используются существующий корневой TSK,
действующие генераторы, игровой плагин и текущие тестовые уровни.

## Журнал автономных решений

### CMT-C01 — подтверждённая объединённая аннотация старше пространственных блокеров

- **Решение:** `initial-network-with-regions.review.json` со статусом
  `author-confirmed`, 982 областями и пустым `reviewIssues` считается
  актуальным фактом карты. Старые записи `initial network state review`,
  `canonical region polygons` и `pending-human-vector-review` считаются
  рассинхронизацией метаданных, а не новыми продуктовыми вопросами.
- **Почему можно принять автономно:** PM уже подтвердил карту и подключение
  областей; решение не расширяет границу, а приводит производные статусы к
  более новому источнику.
- **Пересмотр:** если свежая воспроизводимая геометрическая проверка или
  browser replay обнаружит конкретное пространственное расхождение.

### CMT-C02 — владелец смены фазы владеет производным флагом завершения

- **Решение:** генератор, который создаёт план смены фазы, записывает
  согласованное значение `public.session.canRequestFinish`. Генератор финала
  проверяет этот инвариант, но не переписывает планы других генераторов.
- **Почему можно принять автономно:** это устранение порядка-зависимой сборки
  внутри принятого игрового пакета; публичная форма и серверный guard не
  меняются.
- **Пересмотр:** если единый общий вычисляемый механизм доступности будет
  отдельно принят для всех игр.

### CMT-C03 — две независимые сессии не обязаны повторять случайный порядок

- **Решение:** тест настройки не сравнивает случайные порядки двух сессий и не
  использует вероятностное `notDeepEqual`. Управляемое значение проверяется
  только внутренним `sampleRange`, а повтор принятой команды — сохранённой
  квитанцией без нового обращения к случайности.
- **Основание:** это точное следствие принятого ADR-096.
- **Пересмотр:** только новым архитектурным решением о воспроизводимом
  предварительном выборе.

### CMT-C04 — техническая fixture обязана следовать текущему lifecycle груза

- **Решение:** непубликационная fixture реального хода содержит все поля,
  которые читают обычные планы погрузки, движения и расчёта; её JSON Schema
  запрещает незаметный структурный дрейф.
- **Почему можно принять автономно:** нормативный authoring остаётся источником
  правил, fixture лишь доказывает их и не становится игровым содержимым.
- **Пересмотр:** при следующем изменении принятого cargo lifecycle.

### CMT-C05 — `runtimeReady` включается только после пользовательской приёмки

- **Решение:** два устаревших пространственных блокера снимаются после
  синхронизации, но `runtimeReady` не переключается в `true`, пока нормативный
  ведущий не проведёт все фазы через обычный интерфейс и не пройдут финальные
  production/browser gates.
- **Почему можно принять автономно:** это более строгая поставочная граница,
  не меняющая правила или контракты.
- **Пересмотр:** после зелёной W5.

### CMT-C06 — production-восстановление использует принятую привязку портала

- **Решение:** новую схему токенов не вводить. Принятый ADR-033 и действующий
  путь `portal launch session -> runtime binding` уже возобновляют серверную
  сессию по проверенному портальному контексту; для общей/одноразовой сессии
  новый браузер получает ту же runtime-сессию. Идентификатор и credential не
  передаются как самостоятельное право в URL.
- **Ограничение:** автономный локальный запуск без портального контекста всё ещё
  зависит от того же браузерного профиля. Это явно непроизводственный режим и
  не считается блокером публикации игры через портал.
- **Почему можно принять автономно:** граница доверия уже принята и реализована;
  решение снимает устаревший долг, не меняя безопасность, хранение или API.
- **Пересмотр:** если продукт решит поддерживать долговечные автономные партии
  без портального контекста.

### CMT-C07 — автоматическая браузерная приёмка закрывает технический выпускной gate

- **Решение:** подтверждённая автором карта, три контрольных размера map-first
  интерфейса и полный production E2E обычной партии считаются достаточной
  технической приёмкой для `runtimeReady`. Отдельная субъективная встреча по
  скриншотам остаётся допустимым последующим продуктовым обзором, но не
  удерживает уже проверенную игру в непубликационном состоянии.
- **Почему можно принять автономно:** PM прямо поручил довести реализацию без
  промежуточных согласований; источник геометрии уже имеет статус
  `author-confirmed`, а решение не меняет контракт или правила игры.
- **Пересмотр:** при конкретном визуальном дефекте, новом макете или решении PM
  вернуть ручную визуальную подпись в обязательные ворота выпуска.

## Финальные ворота

Работа считается доведённой до неархитектурной границы, когда:

- генераторы сходятся независимо и производные манифесты актуальны;
- нормативный пакет проходит настройку, новости, обслуживание, рынок, грузы,
  движение, расчёты, строительство, отчётность, методические паузы и финал;
- тот же путь выполняется ведущим через UI без прямой правки состояния;
- карта, панели, формы и итоговый экран приняты на контрольных размерах;
- документация не называет закрытые пространственные вопросы открытыми;
- все намеренно отложенные функции явно отделены от требований текущего
  выпуска.
