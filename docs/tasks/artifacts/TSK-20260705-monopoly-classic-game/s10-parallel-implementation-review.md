# S10: аудит параллельной реализации private invite network v1

Статус: аудит завершён; PM 2026-08-25 принял рекомендованный гибрид. Коммит
`99019ca` сохранён как источник проверенных идей и тестов, но не сливается целиком.

## Основание проверки

Параллельная ветка `agent/simplify-agent-instructions` реализует закрытую
сетевую партию иначе, чем исходный пакет решения S10, принятый PM 2026-08-24;
ниже зафиксированы только отличия исторической ветки:

- приглашение является долговечным многоразовым удостоверением места до
  архивации сессии;
- `joinState` в ветке остаётся неизменяемым `local | private-invite` и не
  описывает занятие места; в принятом гибриде канонично
  `local | invited | joined` с переходом `invited → joined`;
- доставка использует Server-Sent Events (SSE — односторонний HTTP-поток)
  только с номерами версии и события, после которого клиент перечитывает
  полную персональную проекцию по HTTP;
- отдельного WebSocket-протокола и короткоживущего realtime-билета нет.

Проверка выполнена по самому коммиту и в его чистом рабочем каталоге. Прямой
перенос на актуальный `origin/main` был только смоделирован и отменён без
изменения обеих веток.

## Что стоит сохранить

- SSE соответствует фактическому направлению данных: игровые команды уже идут
  по HTTP, а серверу требуется только односторонне сообщить об изменении
  версии. Он не создаёт второй протокол снимков и переиспользует существующий
  защищённый GET и единственный строитель персональной проекции.
- Сервер хранит только SHA-256 удостоверений, назначает actor сам и создаёт
  отдельный ограниченный principal для каждого места.
- URL fragment удаляется до первого асинхронного шага; BFF переносит
  удостоверение в `HttpOnly`, `SameSite=Strict` cookie с именем, зависящим от
  сессии.
- SSE-hub имеет общий предел, heartbeat, объединение накопившихся уведомлений,
  ограниченное ожидание drain и очистку оборванных соединений.
- Нейтральные контракты, browser-safe validators и сценарий двух браузерных
  контекстов можно переиспользовать после композиции с S9.

## Дефекты до интеграции

1. **P1 — гость private preview может заменить весь снимок.** Контракт
   допускает `contentSourceId + accessMode: private-invite`, а
   `restorePreviewSession` проверяет принадлежность сессии, но не доверенную
   роль редактора. Ограниченный участник получает запись полного состояния,
   включая чужие и server-owned поля. Нужны независимый запрет сетевого режима
   для preview и проверка trusted editor/local-controller principal на restore.
2. **P1 — один участник может исчерпать глобальный SSE-пул.** Общий предел 128
   не содержит квоты по `(sessionId, principalId)`, а многоразовый credential
   открывает неограниченное число параллельных потоков. Нужен ровно один
   активный поток на principal с заменой прежнего и общий входной лимит как
   последний предохранитель.
3. **P1 — прямой перенос регрессирует S9.** Ветка основана на старой базе и
   удаляет `participantCount`, диапазон 2–6, `maxParticipants` и сохранение
   состава при reset. `accessMode` должен добавляться ортогонально к уже
   принятой матрице `participantCount × agentSeatCount`.
4. **P2 — импорт другого места молча заменяет cookie текущего principal.** В
   одном профиле host может потерять единственное host/facilitator
   удостоверение, открыв гостевую ссылку. До явного действия переключения BFF
   должен отклонять замену существующего отличающегося principal.
5. **P2 — metadata приглашения не привязана к credential.** BFF доказывает, что
   переданные `seatId/playerId` существуют, но не что credential принадлежит
   им. Проще удалить эти поля из клиентского секрета и считать серверное
   удостоверение единственным доказательством, чем вводить вторую проверку.
6. **P2 — документация занижает browser trust boundary.** Guest credentials
   возвращаются host-браузеру для копирования ссылок, поэтому этот интерфейс и
   исполняемый в нём код временно обрабатывают секреты. Это требует явного
   описания и действующей CSP/XSS-защиты.
7. **P2 — OpenAPI не описывает фактический ответ 429 при заполненном SSE-пуле.**

## Проверка упрощения

Первоначальный пакет S10 с WebSocket добавляет отдельный endpoint выдачи
30-секундных билетов, ограниченный кэш их digest, auth-кадр, subprotocol,
собственную схему полного снимка, коды закрытия и отдельную логику
реконнекта. Для пошаговой партии, где команды уже остаются в HTTP, эти части не
дают дополнительной пользовательской функции по сравнению с SSE-сигналом и
полной HTTP-ресинхронизацией. WebSocket-вариант поэтому является
необоснованным усложнением первого сетевого среза.

Долговечная многоразовая ссылка параллельной ветки, напротив, упрощает систему
за счёт защитного свойства: сохранённая или пересланная ссылка позволяет
повторно получить управление местом. Наиболее узкий качественный вариант между
ними:

1. сохранить SSE с курсором и существующий полный authenticated GET;
2. сохранить одноразовое занятие места и отдельное долговечное participant
   credential в `HttpOnly` cookie;
3. не заводить отдельную таблицу приглашений: до занятия существующая запись
   session principal хранит digest invite, срок и состояние, а одна транзакция
   заменяет его digest новым participant credential и меняет только
   `joinState: invited → joined`;
4. отложить WebSocket, realtime-ticket cache, дельты, presence, Redis и
   горизонтальное масштабирование до измеримого требования.

Этот гибрид сохраняет продуктовую функцию и защиту от повторного использования
ссылки, но удаляет отдельный realtime-протокол и второй краткоживущий секрет.

## Свежие доказательства

- `@cubica/contracts-session`: typecheck и 16/16 тестов — успешно.
- Runtime API: полный набор — `403 pass / 3 skip`; Estate Race package — `53/53`,
  plugin — `37/37` с typecheck; disposable PostgreSQL integration — `2/2`.
- Player Web: полные `328/328`, typecheck и production build — успешно; Estate
  Race two-browser E2E и PostgreSQL restart проходят; desktop+narrow primary
  visual inspection принята для закрытой альфы.
- OpenAPI drift gate — успешно.
- Пробный cherry-pick на актуальный `origin/main` выявил 28 файлов,
  изменённых с обеих сторон, и 43 конфликтных участка; автоматическая
  интеграция неприемлема.

Ограничение закрытой альфы остаётся явным: если claim записан, но ответ с
credential потерян, ведущий пересоздаёт тестовый сеанс. До каталога/production
нужен recoverable handoff; content/economy/product publication и production
readiness остаются отдельными воротами. Браузерная cookie живёт 30 дней,
тогда как runtime credential durable.

Принятый гибрид не переносит многоразовый credential: invite используется ровно
один раз и заменяется durable participant credential. Поэтому перечисленные
выше дефекты исторической ветки не являются принятыми S10-ограничениями.

Принятый процесс координации разных игровых требований и эксклюзивной
shared-реализации записан в
[`docs/processes/parallel-agent-coordination.md`](../../../processes/parallel-agent-coordination.md).
