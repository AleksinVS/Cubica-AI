# S10: решение для закрытой сетевой партии по приглашениям

Статус: требуется решение PM до изменения публичных контрактов, модели
участников, хранения удостоверений и WebSocket-протокола.

## Что уже принято

ADR-059 уже фиксирует модульный монолит `runtime-api`, PostgreSQL как источник
истины, отдельный runtime-issued join-токен для каждого участника,
последовательное исполнение команд, персональную проекцию и WebSocket с полной
ресинхронизацией после реконнекта. S8/S9 уже дали неизменные `seatId`,
`playerId`, `kind`, actor-scoped projection и локальные/агентские места.

Не принято то, как именно живёт секрет приглашения, когда место считается
занятым, как браузер аутентифицирует WebSocket и какие кадры составляют
протокол. Эти детали меняют публичный контракт, доверительную границу и
хранение, поэтому не могут быть выбраны исполнителем автономно.

## Что требуется решить

1. Жизненный цикл приглашения: срок, одноразовость, отзыв и допустимость
   передачи ссылки другому человеку.
2. Жизненный цикл места: какие сетевые значения добавляются к `joinState` и
   какая часть participant может меняться после создания сессии.
3. Аутентификация WebSocket без передачи долговечного runtime credential в
   JavaScript или URL.
4. Минимальный набор кадров, правила версии, коды закрытия и восстановление
   после рестарта процесса.

## Рекомендация

- Создатель private-invite сессии сразу занимает первое человеческое место;
  для остальных человеческих мест runtime один раз возвращает отдельные
  пригласительные ссылки. Обычный creator principal ограничен первым actor;
  facilitator сохраняет только уже объявленные манифестом полномочия. Клиент
  не выбирает `seatId` или `playerId`.
- Join-токен — передаваемая bearer-возможность только до первого успешного
  использования, действует 24 часа и хранится исключительно как SHA-256
  digest. Занятие места атомарно помечает токен использованным и выдаёт новый
  participant credential ровно один раз; Player Web переносит credential в
  session-scoped HttpOnly cookie. Секрет передаётся в URL fragment, а Player
  Web удаляет fragment через `history.replaceState` сразу после claim, поэтому
  он не попадает в HTTP-журналы и Referer. Для ещё не занятого места создатель может
  отозвать приглашение и выпустить замену. Credential действует до архивации
  сессии; повторное использование join-токена запрещено.
- `seatId`, `playerId` и `kind` остаются неизменными. `joinState` расширяется до
  `local | invited | joined` и допускает только переход `invited → joined` в
  одной транзакции занятия места. Состояние текущего соединения не хранится в
  participant и не становится долговечным игровым фактом.
- Браузер не передаёт долговечный credential в WebSocket. Он получает через
  аутентифицированный BFF-запрос одноразовый realtime-ticket на 30 секунд и
  передаёт его в первом WebSocket auth-кадре; до успешной проверки runtime не
  отправляет данные. Ticket хранится как digest в ограниченном in-memory cache
  одного runtime-процесса и потребляется один раз; рестарт просто требует
  получить новый ticket через сохранённый HttpOnly credential.
- Игровые команды остаются в существующем HTTP-контуре. WebSocket первого
  среза — только доставка: после аутентификации и каждого подтверждённого
  изменения runtime отправляет полный персональный `session.snapshot` с
  `stateVersion` и `lastEventSequence`. Старые версии клиент игнорирует.
  Дельты, комнаты, чат и gameplay-команды через WebSocket не вводятся.
- Версия протокола фиксируется WebSocket subprotocol `cubica-session-v1`.
  Клиент отправляет только `session.authenticate`; сервер отправляет только
  `session.snapshot`. Используются стандартные close codes: `1002` для
  неверного протокола, `1008` для недействительного/повторного ticket, `1011`
  для внутренней ошибки и `1012` при рестарте сервиса; причины не содержат
  секретов или внутренних деталей.
- Реестр соединений остаётся в памяти одного процесса. При рестарте соединение
  закрывается, клиент с ограниченной экспоненциальной задержкой получает новый
  realtime-ticket, подключается заново и первым кадром получает полный снимок
  из PostgreSQL. Персистентный реестр соединений и Redis не нужны S10.

Это самый узкий вариант, сохраняющий существующий BFF и HTTP command path:
добавляются один durable invite lifecycle и один короткоживущий WebSocket
ticket, но не второй владелец состояния, очередь доставки или delta-протокол.

## Альтернативы

- Join-токен без срока до занятия проще, но утёкшая ссылка остаётся действующей
  неопределённо долго. Многоразовый join-токен ещё проще для реконнекта, но
  превращается в долговечный credential, который находится в ссылке и доступен
  JavaScript; не рекомендуется.
- Передача participant credential в query string WebSocket не требует ticket
  endpoint, но секрет попадает в URL, журналы и диагностику; не рекомендуется.
- Проксирование WebSocket через Player Web сохраняет HttpOnly cookie до конца,
  но добавляет второй stateful delivery-компонент и расходится с уже принятым
  endpoint в `runtime-api`; не рекомендуется для первого среза.
- Отдельная таблица presence/connection state нужна для нескольких runtime
  реплик, но при принятой одной реплике создаёт лишнее хранение без
  пользовательской функции.

## Что откроет одобрение

После одобрения основной агент уточняет ADR-059 и архитектурный обзор, затем
последовательно проводит: schema-first контракты → транзакционный invite/claim
runtime → WebSocket delivery → Player Web join/reconnect → два браузерных
контекста и restart/resync. Public rooms, matchmaking, spectators, чат,
delta-sync и горизонтальное масштабирование остаются вне S10.
