## Статус документа

Все варианты ниже — `Proposed`. Документ не является ADR и не принимает
решение за PM. После ответа PM выбранная долговременная граница отражается в
существующем профильном ADR либо в самом узком новом ADR, а затем — в
`docs/architecture/PROJECT_ARCHITECTURE.md`.

Независимые fail-closed исправления не ждут этих решений. Останавливается
только соответствующий поток.

## AD-01. Коммерческие условия и атомарность платежа

**Что нужно решить.** Кто является источником истины цены, пакета и срока
покупки, и при каком состоянии Portal подтверждает платёж провайдеру.

**Почему сейчас.** Текущий endpoint принимает коммерческие условия от клиента,
а callback может пометить заказ оплаченным и ответить `OK`, даже если purchase
не создана. При включении Robokassa это даёт и занижение цены, и оплату без
доступа.

**Рекомендация.** До завершения работы оставить реальный Robokassa path
выключенным. Затем:

1. сервер выводит цену и срок из версионированного каталога предложения;
2. order хранит неизменяемый snapshot предложения и ожидаемую сумму;
3. callback сверяет точную сумму и валюту с order;
4. создание/нахождение purchase и перевод order в `paid` выполняются одной
   идемпотентной транзакцией;
5. ACK отправляется только после commit, повтор достраивает отсутствующий
   эффект, не дублируя purchase.

**Альтернативы.**

- Оставить платежи stub-only: безопаснее и дешевле сейчас, но не даёт реальной
  продажи.
- Разрешить произвольную цену клиенту как donation/pay-what-you-want: меняет
  продуктовую модель и всё равно не устраняет атомарность.

**Что разрешает одобрение.** Проектирование schema/migration order snapshot,
транзакционной state machine и реального payment integration test.

## AD-02. Возобновление Runtime-сессии

**Что нужно решить.** Как тот же браузер и новое устройство повторно получают
доступ к уже созданной Runtime-сессии, не раскрывая долговечный bearer Portal
или browser JavaScript.

**Почему сейчас.** Portal хранит только `runtime_session_id`; защищённый GET
без bearer отвечает 401. Первый браузер уже имеет HttpOnly credential у Player
BFF, но Portal не умеет безопасно подтвердить или восстановить эту связь.

**Рекомендация.**

- Для того же браузера Player BFF использует имеющийся session-scoped HttpOnly
  credential после server-side проверки `runtimeSessionId`.
- Для нового устройства Portal выдаёт одноразовый короткоживущий claim,
  связанный с portal principal, binding и назначением. Player BFF обменивает
  его server-to-server на новую credential; claim нельзя повторить или
  использовать для другой сессии.
- Portal не хранит и не возвращает сырой Runtime bearer.

**Альтернативы.**

- Не поддерживать новое устройство в первой версии и честно объявить
  device-local resume. Дешевле, но ограничивает купленный доступ.
- Хранить Runtime bearer в Portal. Проще, но расширяет blast radius и не
  рекомендуется.

**Что разрешает одобрение.** Контракт claim/reissue, срок и replay policy,
storage migration binding и двухустройственный E2E.

## AD-03. Идемпотентное создание Portal binding

**Что нужно решить.** Какая сторона владеет ключом идемпотентности создания
Runtime-сессии и как устраняются orphan sessions после частичного сбоя.

**Почему сейчас.** Portal сначала создаёт Runtime-сессию, а затем вставляет
unique binding. Два запроса могут создать две Runtime-сессии, после чего одна
вставка проиграет.

**Рекомендация.** Portal атомарно резервирует binding с устойчивым operation
id, затем передаёт этот id Runtime как idempotency key. Повтор возвращает ту же
Runtime-сессию. Незавершённая reservation имеет ограниченное состояние
recovery, а orphan cleanup является страховкой, не основным механизмом.

**Альтернативы.**

- Только Portal reservation без Runtime idempotency: проще, но сбой после
  Runtime create и до записи результата остаётся неоднозначным.
- Создавать Runtime session внутри распределённой транзакции: несоразмерно
  сложно для текущей архитектуры и не рекомендуется.

**Что разрешает одобрение.** Расширение public/internal Runtime contract,
миграция Portal binding и concurrency/recovery tests.

## AD-04. Совместимость Cubica Surface

**Что нужно решить.** Обязательны ли версия каталога компонентов и JSON Schema
props при приёме `CubicaSurface`.

**Почему сейчас.** Текущий renderer принимает неизвестную версию каталога и
не проверяет props по объявленным схемам. Это превращает schema metadata в
неисполняемую документацию.

**Рекомендация.** Fail closed: envelope содержит поддерживаемую точную major
версию каталога, каждый component type имеет каноническую JSON Schema props,
а renderer валидирует document до монтирования. Неизвестная версия или
невалидные props дают безопасный unavailable surface.

**Альтернативы.** Best-effort рендер неизвестных optional-компонентов. Лучше
для forward compatibility, но требует отдельной формальной семантики
required/optional и частичной валидации.

**Что разрешает одобрение.** Schema/contract change, generated types,
renderer validator и compatibility fixtures.

## AD-05. Деградация hybrid-игры

**Что нужно решить.** Должна ли hybrid-игра продолжать детерминированные
действия при недоступном Agent Runtime.

**Почему сейчас.** Сейчас недоступность агента блокирует всю игру, хотя часть
действий не требует модели. Название `hybrid` само по себе не задаёт
продуктовую гарантию.

**Рекомендация.** Manifest явно объявляет failure policy:

- `agent-required` — честный полный pause;
- `deterministic-fallback` — опубликованные детерминированные actions остаются
  доступны, agent-owned actions показывают unavailable.

Default для существующих пакетов — `agent-required`, чтобы не менять
поведение молча. Fallback разрешается только пакету, который доказал
согласованное продолжение нейтральной fixture.

**Альтернативы.** Один глобальный policy для всех hybrid-игр проще, но слишком
сильно связывает игры с разными правилами.

**Что разрешает одобрение.** Расширение manifest schema, runtime readiness,
Player UX и neutral/game fixtures.

## AD-06. Доверенный origin предпросмотра

**Что нужно решить.** Откуда Editor и Player получают доверенный origin
другой стороны preview-моста.

**Почему сейчас.** Точное сравнение origin уже есть, но ожидаемое значение
задаёт сам родитель. Компрометация или неправильная конфигурация родителя
разрушает смысл проверки.

**Рекомендация.** На первой hosted-границе сервер формирует allowlist точных
origin из deployment config и передаёт его обеим сторонам в подписанной
session bootstrap-проекции. Динамический capability-token не вводить, пока
нет нескольких preview-hosts или cross-origin federation.

**Альтернативы.** Signed per-preview capability гибче, но добавляет issuance,
expiry/replay и key rotation раньше реального потребителя.

**Что разрешает одобрение.** Изменение bootstrap/trust contract и hosted E2E.

## AD-07. Гарантия ИИ-разбора

**Что нужно решить.** Обещает ли платформа семантически истинный безопасный
разбор или только структурированный черновик для обязательной проверки
ведущим.

**Почему сейчас.** JSON Schema доказывает форму и существование ссылок на
события, но не может доказать отсутствие психологического диагноза или связь
утверждения с конкретным событием. ADR-104 формулирует более сильную гарантию,
чем реализованный контроль.

**Рекомендация для текущего этапа.** Честно сузить гарантию до
`human-reviewed draft`: интерфейс и экспорт явно маркируют черновик,
публикация без действия ведущего невозможна, prompt/schema выполняют
структурные ограничения, а семантическая истинность не заявляется.

**Альтернатива.** Ввести отдельный semantic moderation/evidence-verification
контур с моделью угроз, eval-набором и policy. Это дороже, само остаётся
вероятностным и требует отдельной продуктовой метрики качества.

**Что разрешает одобрение.** Уточнение ADR-104, текстов UI и acceptance/eval
границы либо проектирование нового moderation-контура.

## Что не требует решения PM

Не требуют нового решения исправления F-001..F-025, F-029..F-030,
F-035..F-046 и F-048..F-049, пока они восстанавливают уже принятый инвариант
без смены публичной формы, source of truth или постоянного хранения. Для
F-035 таким основанием служит одобренное code-owned закрытие core routes в
`TSK-20260803-portal-access-control`; D-009 уточняет только часть ADR-006,
уже заменённую Accepted ADR-059.

Если во время реализации выяснится, что минимальный безопасный вариант всё же
меняет такую границу, останавливается только этот блок; факт и варианты
добавляются сюда до изменения кода.
