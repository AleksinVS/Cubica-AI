## 1. Назначение

Процесс разрешает разным игровым агентам независимо исследовать похожие
возможности, сохраняя правильные и дополняющие друг друга требования. Он
предотвращает только конкурирующую запись одного общего платформенного
контракта.

Одинаковое игровое слово не образует shared-границу само по себе. Например,
аукционы разных игр могут разделять нейтральные операции выбора, ротации и
атомарного перевода ресурса, но сохранять разные правила допуска, ставки,
завершения и владения внутри игр.

Процесс не меняет runtime Cubica, игровые контракты или полномочия PM. Решения о
публичном контракте, источнике истины, доверии, безопасности, хранении и
совместимости по-прежнему принимает PM.

## 2. Координатор

Основной агент каждого корневого `TSK-*` является его координатором. Это
временная роль задачи, а не отдельный сервис или постоянный глобальный агент.
Название модели и конкретная агентская среда не входят в контракт.

Координатор:

- читает корневой TSK, принятые решения и актуальные ветки;
- декомпозирует работу и назначает исполнителей;
- не допускает двух писателей одной shared-границы;
- получает handoff и проверяет фактический diff;
- по умолчанию сам интегрирует зависимые ветки;
- назначает отдельного интегратора только при конфликтующих требованиях игр,
  критическом shared-контракте или необходимости независимой композиции;
- сериализует полные проверки, build и E2E на общем хосте;
- освобождает владение после передачи, блокировки или принятия результата.

Координатор не принимает архитектурные решения вместо PM и не объявляет
игровую политику универсальной без нейтрального доказательства.

## 3. Режимы владения

Используются только два режима:

| Режим | Параллельность | Shared-запись |
| --- | --- | --- |
| `open` | несколько игр и агентов | запрещена |
| `exclusive` | один назначенный писатель | разрешена в точной границе |

`blocked`, `review` и `done` остаются обычными статусами задачи, а не режимами
владения. Адаптация игр после общего контракта — обычная параллельная работа с
непересекающимися путями и не требует третьего режима.

Игровая работа внутри `games/<game>/**` не регистрируется глобально, пока не
предлагает изменение shared-схемы, Mechanics IR, runtime, общего player-слоя,
хранения или trust boundary.

## 4. Требования разных игр

В режиме `open` каждый игровой агент сначала пытается выразить сценарий через
существующий Game Intent -> typed Mechanics IR путь. При доказанном пробеле он
останавливает shared-правки и передаёт координатору пять пунктов:

```text
Игра и наблюдаемый сценарий
Обязательный инвариант
Политика, которая должна остаться внутри игры
Доказанный пробел существующей платформы
Тест приемки
```

Координатор сопоставляет известные требования и выбирает минимальный результат:

- общая нейтральная возможность с игровыми данными в manifest;
- общее ядро и разные игровые политики;
- независимые игровые композиции без нового shared-компонента;
- остановка для решения PM, если гарантии несовместимы.

Наличие второй игры не является искусственным шлюзом для малой общей
возможности: достаточно конкретного игрового сценария и нейтральной fixture.
Но уже известное активное требование другой игры нельзя игнорировать.

## 5. Эксклюзивная shared-правка

Перед назначением shared-писателя координатор проверяет раздел `Active shared
changes` в `NEXT_STEPS.md`. В нём публикуются только активные `exclusive`
изменения:

```text
Boundary | Task | Coordinator | Owner | Working/integration branch
```

Граница называется по конкретному общему контракту или операции, например
`SessionParticipants` или `core.entities.order`, а не по общему игровому слову
вроде «аукцион».

Для одной границы допускается одна строка и один писатель. Исследования режима
`open` в таблицу не попадают. Claim считается действующим только после того,
как отдельный coordination commit попал в актуальный `origin/main` обычным
принятым способом. До начала shared-записи координатор повторно выполняет
`fetch` и проверяет уникальность границы. Конкурирующий non-fast-forward или уже
опубликованная строка оставляет новый блок в `open` и запускает синтез
требований вместо параллельной реализации.

`Working/integration branch` содержит обычную рабочую ветку единственного
писателя либо отдельную integration branch, если она действительно требуется.

Если shared-изменение требует архитектурного решения, `exclusive` открывается
только после решения PM. Для schema-first изменения канонический контракт и
нейтральные тесты интегрируются раньше зависимых consumers.

## 6. Передача и интеграция

Минимальный handoff содержит:

```text
Head SHA
Что изменено
Какие проверки прошли
Что осталось
Риски или блокер
```

Base SHA и принятые решения фиксируются в исходном задании или корневом TSK и
не дублируются в каждой игровой карточке.

Отдельная интеграционная ветка создаётся только для shared-контракта, двух и
более зависимых веток либо ручной композиции разных баз. В остальных случаях
координатор использует обычный поток завершения ветки.

Для зависимой композиции координатор:

1. создаёт integration branch от свежего `main`;
2. интегрирует один канонический contract commit, если контракт меняется;
3. выдаёт его точный SHA зависимым исполнителям;
4. принимает обратно их head SHA и проверяет смысловой diff;
5. сохраняет все затронутые принятые slices и baselines;
6. один раз синхронизирует результат со свежим `main` без переписывания
   истории;
7. последовательно выполняет итоговые проверки.

Авторы зависимых веток не сливают их самостоятельно. Смысловой конфликт не
разрешается как обычный текстовый merge conflict и возвращает работу в `open`
либо к решению PM.

## 7. Другие агентские среды

Координатором может быть основной агент Codex, другой агентской среды или
человек. Среде достаточно уметь читать Git-репозиторий, работать в
изолированной ветке или копии, запускать команды и возвращать handoff с head
SHA.

Внутренние сообщения, названия моделей и API запуска субагентов являются
адаптерами среды. Долговременное состояние находится в Git, TSK, ADR/GSR и
Handoff Log, а не в истории чата. Если координатор остановился, PM или новый
основной агент принимает роль по этим материалам и явно фиксирует передачу.

В Codex выбор исполнителей дополнительно регулирует
`skills/C_codex-agent-routing/SKILL.md`. Другая среда использует эквивалентное
риск-ориентированное распределение, не меняя общий процесс.

## 8. Проверка и остановка

Shared-изменение принимается при наличии:

- нейтрального теста без идентификатора и терминов конкретной игры;
- игровых сценариев, чьи требования повлияли на решение;
- регрессий всех затронутых принятых slices и baselines;
- schema/generation проверок для декларативных контрактов;
- negative-path тестов при изменении атомарности, приватности или повторов;
- аудита отсутствия game ID, фаз, клеток, ресурсов и числовых правил игры в
  shared production-коде;
- независимого ревью, соразмерного риску.

Координатор останавливает shared-работу, если требуется неодобренное решение
PM, требования игр несовместимы, нейтральная граница содержит игровую
семантику, ветка основана на устаревшем решении либо недостаток платформы не
отделён от ошибки game authoring.

## 9. Не вводится

Текущий процесс не добавляет:

- coordination service, базу агентов, аренды или heartbeat;
- обязательный CLI или JSON Schema handoff;
- автоматическое назначение моделей и разрешение конфликтов;
- постоянную integration branch для каждой локальной задачи;
- обязательную merge queue.

Read-only preflight имеет смысл только после повторения одной и той же
координационной ошибки; он не сможет принимать решения или выполнять merge.
