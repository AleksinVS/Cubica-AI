# Product Context Shadow: активация и смысловая оценка

Runbook отделяет закрытую синтетическую CLI-репетицию от каждого отдельно
разрешённого реального shadow-окна. Успех репетиции не разрешает внешний вызов,
а результат одного реального окна не переносится на следующее.

## Цель и границы

Используются фиксированные синтетические сообщения, локальный шлюз,
возвращающий `no_change`, и одноразовый bare Git в `.tmp/`, открытый только
для чтения. PostgreSQL — отдельная shadow-база с непривилегированным
runtime-login; миграция и membership роли подготавливаются оператором.

Репетиция не включает `PKS_KEY`, Z.AI или сеть, запуск Portal/Editor,
реальный bearer, пользователя, игру или wiki, применение миграции, cron,
секреты или TLS, а также записи в канон, Stage 1 или рабочий Git.

## Что готовит оператор

Оператор подготавливает изолированную shadow PostgreSQL и проверяет, что
runtime-login подключается только через loopback и имеет только заранее подготовленное membership в
`product_context_shadow_app`. Секреты, логины и адреса не записываются в
отчёты и команды примеров.

Также оператор создаёт временный bare Git под `.tmp/`, оставляет его без
изменений и предоставляет CLI read-only путь к нему. В репозитории нет
пользовательских, проектных или секретных данных.

## Автоматические проверки

Команды уже включают обязательные защитные флаги; дополнительные аргументы
передавать не нужно:

1. `npm run preflight:shadow:synthetic --workspace @cubica/product-context`;
2. после успешного preflight —
   `npm run run:shadow:synthetic --workspace @cubica/product-context`.

Preflight подтверждает test/staging, непривилегированный runtime-login,
подготовленную схему/роль и возможность открыть временный bare Git только для
чтения. Run использует встроенные фиксированные сообщения и локальный
`no_change` gateway, выполняет один shadow-run и его точный повтор с тем же
устойчивым ключом, после чего подтверждает идемпотентность и неизменность Git.
Код не читает provider credentials и не создаёт сетевой gateway.

Ожидаемый вывод содержит только `ready`, `no_change`, признаки точного повтора,
число локальных вызовов gateway и признак неизменности Git. Тексты, содержимое
wiki, адреса баз и репозиториев, bearer и секреты в выводе запрещены.

## Операторские ворота активации

Зелёный preflight не разрешает реальный shadow. Оператор отдельно подтверждает
отдельную базу и runtime-login с membership роли, test/staging, доверенный
origin и раздельные HMAC-ключи, серверный read-only bare Git с разрешённой
ревизией, разрешающую политику provider, одного разработчика и одну игру,
ограниченный объём и план хранения/удаления. В репетиции должны отсутствовать
`PKS_KEY`, реальный bearer и реальные тексты.

Каждый пункт получает отметку подтверждён, отклонён или не проверен. До
подтверждения всех пунктов режим остаётся выключенным.

## Смысловое оценочное окно

После успешного первого реального `no_change` следующий операторский блок не
требует отдельного постоянного runner. Используется тот же выключенный
теневой путь, а в одно короткое окно входят ровно пять заранее определённых
одноходовых категорий:

1. переходная беседа без долговременного знания — `no_change`;
2. факт, уже присутствующий в разрешённой wiki, — `no_change`;
3. двусмысленное или только предложенное агентом решение без подтверждения
   пользователя — `no_change`;
4. явно подтверждённое новое долговременное решение — `proposal`;
5. явная коррекция существующего знания — `proposal`.

Между сценариями нельзя менять prompt, повторять неудачный вызов или добавлять
новый пример. Для каждого устойчивого ключа ожидаются два точных сообщения,
один run и одна бесконтентная metric; Portal каждый раз заново проверяет JWT,
роль и владение той же игрой. HEAD read-only Git до и после окна должен
совпасть.

Положительный результат проходит не только серверную JSON Schema и проверки
хэшей, области, источников и итоговой страницы, но и локальную смысловую
оценку уполномоченным оператором: только подтверждённые факты, правильная
страница, минимальная локальная правка, отсутствие домыслов, дубликатов,
противоречий и побочного переписывания. В постоянный отчёт попадают только
категория, ожидаемый и фактический исход, четыре логических признака, число
операций, задержка, байты, неизменность Git и результат очистки. Тексты,
пути, ссылки, идентификаторы и содержимое кандидата не сохраняются.

Ошибка схемы или шлюза, неподходящий кандидат, изменение прав или Git и
неполная очистка немедленно останавливают окно. Неожиданный `no_change`
считается сигналом качества и не разрешает ad-hoc повтор. Новое окно требует
нового явного решения с тем же набором операторских ворот.

## Отказ и повтор

Несоответствие preflight, внешний флаг, сетевой вызов, запись в Git,
неожиданный bearer или содержательный вывод означает отказ с кодом ошибки.
Отказ закрывает run и не меняет основной ответ, канон или Stage 1.

Точный повтор, доказывающий идемпотентность, выполняется внутри одной команды
`run`. После отказа оператор сначала выясняет, успел ли запуск записать
состояние. Неизвестный результат оборванного запуска не считается успехом, а
команду нельзя слепо перезапускать на той же базе. Неустранённый отказ
передаётся оператору без обхода проверки.

## Откат и очистка

При отказе оператор выключает synthetic-run, удаляет только созданные в
`.tmp/` bare Git и журналы репетиции, отзывает временное membership или доступ
runtime-login и выполняет предусмотренную ограниченную очистку shadow-данных.
Очистка выводит только количества.

Не удаляются рабочий Git, Stage 1, производственная база, wiki, секреты или
данные других прогонов. Отдельная база удаляется оператором по обычной
процедуре после проверки связанных запусков; команды с секретами здесь не
приводятся.

## Критерии готовности

Репетиция подготовлена, но не активирована, когда preflight и run выполнены в
закрытом режиме, локальный gateway вернул `no_change`, точный retry дал
идемпотентный результат, Git остался неизменным, внешний вызов не выполнялся,
а вывод не содержит содержимого и секретов. Отчёт хранит только команды,
статусы и количества.

Этот результат разрешает лишь запрос на отдельное одобрение реального
непроизводственного shadow-прогона и не является таким одобрением.

## Фактический первый реальный прогон

PM 2026-08-11 отдельно одобрил один непроизводственный прогон, определил его
как pet-test, выбрал Coding Plan и подтвердил разработчика `abc` владельцем
`Antarctica`. Это решение не меняет синтетический характер команд выше и не
является повторно используемым разрешением для production, SaaS или публичного
контура.

Оператор подготовил одноразовые PostgreSQL 17 database/login, HMAC-ключи,
Portal/Editor env и read-only bare Git. Реальный HTTP preflight доказал `401`
без корректного JWT и `200 allow` только после повторной серверной проверки
роли и владельца. Один диалог прошёл через локального помощника Editor и Z.AI:
основной SSE-ответ сохранил статус `200`, shadow завершился `no_change`, а Git
не изменился.

После 60-секундного срока cleanup удалил run и metric, заменил оба точных
сообщения tombstone-записями и оставил ноль активных байтов текста. Затем
временные база, runtime-role, ключи и bare Git были удалены. В отчёте сохранены
только статусы, количества, задержка и признаки неизменности; тексты, bearer,
ключи, строки подключения и содержимое wiki не сохранялись.

Прогон выявил и закрыл два операционных дефекта: автоматически добавленный
Strapi role-permission scope блокировал маршрут до Portal-контроллера, а
cleanup CLI использовал неподдерживаемый strip-only запуск TypeScript. JWT и
предметные проверки Portal не отключались; cleanup переведён на отдельный
`vite-node` wrapper. Следующий реальный прогон требует нового явного решения и
повторной подготовки всех операторских ворот.

## Фактическая первая попытка смысловой оценки

PM поручил продолжить Stage 2, что было применено как разрешение одного
пятисценарного Coding Plan окна в прежнем непроизводственном pet-test контуре
`abc → Antarctica`. Первые три отрицательные категории завершили coordinator:
их terminal result и metric были атомарно сохранены в одноразовой PostgreSQL.
Однако временный evaluator дополнял постоянную бесконтентную сводку только
после всей матрицы, поэтому после hard stop и удаления базы фактические
`no_change/proposal` исходы этих трёх случаев недоступны. Первый положительный
сценарий завершился безопасным отказом координатора; пятый вызов не выполнялся.

Сырые ответы provider по проектному правилу не журналировались, поэтому после
удаления одноразовой базы нельзя достоверно выбрать между malformed payload,
HTTP/quota, timeout и другими закрытыми причинами. Этот недостаток отчёта не
ослабляет безопасность, но означает, что окно не доказало смысловое качество.
Статический Sol high разбор обнаружил отдельный воспроизводимый пробел в
инструкции модели: она не описывала полный формат новой Markdown-страницы,
выбор новой страницы для нового предмета, запрет полной замены файла и
сохранение старого происхождения при локальной правке.

Исправление ограничено prompt существующего Z.AI adapter и regression-тестами
валидного создания и локального update. Серверная JSON Schema, нормализация,
проверки происхождения, `cubica_id`, области и exact anchors не ослаблены.
Повторный внешний вызов не входит в исправление: для него оператор снова
получает явное разрешение, подготавливает одноразовый контур и заново запускает
всю неизменную пятисценарную матрицу без промежуточной настройки prompt.
После каждого завершённого сценария evaluator должен до следующего вызова
дополнять отдельный постоянный бесконтентный отчёт, не перенося в него тексты,
пути, ссылки или содержимое кандидата. Runtime terminal result + metric
по-прежнему атомарно сохраняются существующим coordinator в одноразовой базе.

После отказа одноразовые shadow database/login/roles, точные сообщения, ключи,
bearer, копия Portal-базы и bare Git удалены; временный Portal остановлен.
Исходная Portal-база, канон и рабочий Git не изменялись.

## Фактическая повторная попытка смысловой оценки

PM 2026-08-11 явно разрешил новое неизменное пятисценарное Coding Plan окно.
Перед первым вызовом одноразовый evaluator синтетически подтвердил атомарную
запись, `fsync`, повторное чтение, строгий набор бесконтентных полей и права
`0600`. После каждого вызова он сохранял отдельный результат до решения о
следующем вызове.

Первый сценарий переходной беседы и второй сценарий уже известного факта дали
ожидаемый `no_change` за 3990 и 3536 мс. Третий сценарий неподтверждённого
предложения агента не дал смыслового результата: шлюз достиг фиксированного
15-секундного лимита и coordinator атомарно завершил run с
`gateway_timeout`. Это транспортный отказ, а не подтверждение или опровержение
правильности семантической классификации. В соответствии с hard-stop правилом
повтора не было, а сценарии нового решения и коррекции не запускались.

Постоянный бесконтентный отчёт сохранил точные исходы всех трёх выполненных
сценариев, число операций, задержку, объём и неизменность Git; тексты, пути,
ссылки, идентификаторы, сырые ответы и кандидаты в него не попадали. После
двухминутного срока хранения cleanup удалил 3 run и 3 metric, обезличил 6
сообщений и 3 потока и оставил 0 активных текстовых байтов. Затем временные
Portal, PostgreSQL database/login, HMAC/JWT, копия Portal-базы и bare Git были
удалены. Исходная Portal-база, канон и рабочий Git не менялись.

Окно не принимается: требуемая матрица `no_change, no_change, no_change,
proposal, proposal` не завершена. Один сетевой timeout не является основанием
менять prompt, ослаблять серверную проверку или повышать лимит автоматически.
Новая попытка требует отдельного явного разрешения и повторной подготовки всех
операторских ворот; Stage 3, активное чтение и Git-запись по-прежнему запрещены.
