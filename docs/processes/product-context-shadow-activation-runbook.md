## Цель и границы

Используются фиксированные синтетические сообщения, локальный шлюз,
возвращающий `no_change`, и одноразовый bare Git в `.tmp/`, открытый только
для чтения. PostgreSQL — отдельная shadow-база с двумя непривилегированными
login: приложение может только поставить задание, worker — только вызвать
фиксированные функции очереди. Миграции и memberships ролей подготавливаются
оператором.

Репетиция не включает `PKS_KEY`, Z.AI или сеть, запуск Portal/Editor,
реальный bearer, пользователя, игру или wiki, применение миграции, cron,
секреты или TLS, а также записи в канон, Stage 1 или рабочий Git.

## Текущее состояние

После четырёх исторических окон синтез перенесён в устойчивую PostgreSQL-
очередь. Editor дожидается только ограниченной авторизации и записи задания;
языковую модель вызывает отдельная one-shot worker-команда. Worker использует
отдельный login с доступом только к фиксированным функциям очереди, не хранит
bearer и повторно проверяет Portal и точные сообщения до и после модели.

Приведённые ниже фактические окна сохраняются как история доказательств, а не
как инструкция повторить прежний одноразовый процесс. Постоянный
evaluator/runner реализован как поддерживаемая непроизводственная команда и
локально принят. Он не ставит задания и не создаёт второй queue/storage/service:
наблюдает только ход, уже поставленный штатным Editor/Portal, и передаёт worker
точный target owner/game/stable key. Окно DR-16 израсходовано 2026-08-24 и
остановлено на ложном `proposal` для уже существующего знания. Stage 3,
активное чтение, применение кандидатов и Git-запись остаются закрыты.

## Что готовит оператор

Оператор подготавливает изолированную shadow PostgreSQL и проверяет, что оба
login подключаются только через loopback. App-login имеет единственное
membership в `product_context_shadow_app`, worker-login — единственное
membership в `product_context_shadow_worker`. Секреты, логины и адреса не
записываются в отчёты и команды примеров.

Также оператор создаёт временный bare Git под `.tmp/`, оставляет его без
изменений и предоставляет CLI read-only путь к нему. В репозитории нет
пользовательских, проектных или секретных данных.

Для evaluator оператор заранее создаёт manifest: CLI его не создаёт. Это
owned regular JSON-файл с правами `0600`, точным `schema_version`, одним
`shadow_principal_ref`, единственным `applies_to`, ожидаемым Git HEAD и пятью
фиксированными категориями в порядке с их `stable_turn_key`. Пути передаются
через `CUBICA_PRODUCT_CONTEXT_SHADOW_EVALUATION_MANIFEST`,
`CUBICA_PRODUCT_CONTEXT_SHADOW_EVALUATION_REPORT` и
`CUBICA_PRODUCT_CONTEXT_SHADOW_EVALUATION_WORKTREE`; manifest и distinct report
path должны быть абсолютными и находиться под `worktree/.tmp`. Report может
отсутствовать до preflight. Цепочка каталогов должна принадлежать оператору и
не иметь group/world write; `0700` рекомендуется. Реальные ID и тексты в
manifest, report, командах и выводе не публикуются.

## Автоматические проверки

Команды уже включают обязательные защитные флаги; дополнительные аргументы
передавать не нужно:

1. `npm run preflight:shadow:synthetic --workspace @cubica/product-context`;
2. после успешного preflight —
   `npm run run:shadow:synthetic --workspace @cubica/product-context`.

Preflight подтверждает test/staging, оба непривилегированных login, точные
memberships подготовленных ролей и возможность открыть временный bare Git
только для чтения. Run использует встроенные фиксированные сообщения и локальный
`no_change` gateway, выполняет один shadow-run и его точный повтор с тем же
устойчивым ключом, после чего подтверждает идемпотентность и неизменность Git.
Код не читает provider credentials и не создаёт сетевой gateway.

Ожидаемый вывод содержит только статусы и бесконтентные количества. Постоянный
контур запускается режимами `preflight`, `run-next`, `review`, `cleanup`:
`npm run evaluate:shadow --workspace @cubica/product-context -- <mode>`.
Manifest и report — разные абсолютные пути внутри принадлежащего оператору
worktree; каталоги принадлежат оператору и не допускают group/world write
(`0700` рекомендуется), а файлы имеют точные права `0600`. Report
записывается атомарно после каждого сценария. `review` показывает локальный
raw material вручную через `/dev/tty`, но сохраняет только четыре булевых
признака. Тексты, содержимое wiki, адреса баз и репозиториев, bearer и секреты
в выводе запрещены.

При `gateway_malformed` команда `run-next` дополнительно выводит в `stderr`
только один проверенный этап: `provider_http`, `provider_envelope`,
`candidate_json`, `proposal_structure`, `exact_patch`, `result_schema`,
`result_binding`, `timestamp_binding`, `provenance` или `final_page_policy`.
Код берётся из существующего `last_error_code`, не попадает в metric/report и
удаляется штатным cleanup вместе с run. Неизвестное значение не выводится;
текст provider, candidate, путь, ссылка, AJV error и причина исключения
запрещены. Оператор фиксирует allowlisted stage в журнале задачи до cleanup.

Пять заданий нельзя помещать в очередь заранее: evaluator допускает только
уже проверенный текущий target и запрещает будущие run. Оператор выполняет
последовательность `enqueue-next -> run-next -> review` отдельно для каждого
сценария; следующий enqueue разрешён только после сохранённой смысловой
проверки предыдущего результата.

## Операторские ворота активации

Зелёный preflight не разрешает реальный shadow. Оператор отдельно подтверждает
отдельную базу, app- и worker-login с единственными memberships, test/staging,
доверенный origin и раздельные HMAC-ключи, серверный read-only bare Git с
разрешённой ревизией, разрешающую политику provider, одного разработчика и
одну игру, ограниченный объём и план хранения/удаления. В репетиции должны
отсутствовать `PKS_KEY`, реальный bearer и реальные тексты.

Каждый пункт получает отметку подтверждён, отклонён или не проверен. До
подтверждения всех пунктов режим остаётся выключенным.

## Смысловое оценочное окно

Исторические одноразовые окна использовали тот же выключенный теневой путь и
ровно пять заранее определённых одноходовых категорий. Следующее окно должно
воспроизвести эту матрицу уже через принятый постоянный evaluator/runner:

1. переходная беседа без долговременного знания — `no_change`;
2. факт, уже присутствующий в разрешённой wiki, — `no_change`;
3. двусмысленное или только предложенное агентом решение без подтверждения
   пользователя — `no_change`;
4. явно подтверждённое новое долговременное решение — `proposal`;
5. явная коррекция существующего знания — `proposal`.

Между сценариями нельзя менять prompt, повторять неудачный вызов или добавлять
новый пример. Для каждого устойчивого ключа ожидаются два точных сообщения,
один run и одна бесконтентная metric; Portal каждый раз заново проверяет JWT,
роль и владение той же игрой. HEAD read-only Git до и после окна должен
совпасть.

Положительный результат проходит не только серверную JSON Schema и проверки
хэшей, области, источников и итоговой страницы, но и локальную смысловую
оценку уполномоченным оператором: только подтверждённые факты, правильная
страница, минимальная локальная правка, отсутствие домыслов, дубликатов,
противоречий и побочного переписывания. В постоянный отчёт попадают только
категория, ожидаемый и фактический исход, четыре логических признака, число
операций, задержка, байты, неизменность Git и результат очистки. Тексты,
пути, ссылки, идентификаторы и содержимое кандидата не сохраняются.

Ошибка схемы или шлюза, неподходящий кандидат, изменение прав или Git и
неполная очистка немедленно останавливают окно. Неожиданный `no_change`
считается сигналом качества и не разрешает ad-hoc повтор. Новое окно требует
нового явного решения с тем же набором операторских ворот.

DR-12 прошёл свежую Sol-high приёмку. Обязательный `manifest_digest` в
maintained report равен `sha256:` + SHA-256 точных байтов manifest. Evaluator
сверяет его на каждом lifecycle entry и перед удалением manifest; sidecar и его
env-переменная не используются. Разрешение DR-13 израсходовано, поэтому новый
внешний запуск снова закрыт до отдельного решения PM.

DR-15 реализован как внутренняя диагностика без изменения JSON Schema,
таблиц, metric или постоянного report. Окно DR-16 с model timeout 45000 ms,
Portal auth timeout 5000 ms, lease 60000 ms, retention 300000 ms,
`maxAttempts=1` и без retry израсходовано после двух вызовов: второй дал ложный
`proposal` и hard stop. Exact-zero cleanup завершён. Любой новый внешний
запуск требует отдельного решения PM и свежего Sol-high preactivation.

Для одноразового локального контура не требуется поднимать Next.js: текущий
AG-UI route и локальная editor personality могут быть вызваны как серверные
модули, сохраняя штатные Portal authorization и PostgreSQL enqueue. Portal
запускается server-only через официальный Strapi programmatic API без admin UI.
Это операционное упрощение не создаёт второй evaluator, queue/storage boundary
или поддерживаемый сервис и особенно важно на хосте с ограниченной памятью.

## Отказ и повтор

Несоответствие preflight, внешний флаг, сетевой вызов, запись в Git,
неожиданный bearer или содержательный вывод означает отказ с кодом ошибки.
Отказ закрывает run и не меняет основной ответ, канон или Stage 1.

Точный повтор, доказывающий идемпотентность, выполняется внутри одной команды
`run`. Асинхронный worker повторяет только явно временный отказ, для которого
provider доказуемо отклонил запрос до обработки. Timeout, разрыв транспорта,
непроверенный `5xx` или истёкший `calling_model` дают неизвестный исход и не
повторяются. Quota, subscription, credentials, entitlement и fair-use требуют
операторского устранения причины. Неустранённый отказ передаётся оператору без
обхода проверки.

## Откат и очистка

При отказе оператор выключает synthetic-run, удаляет только созданные в
`.tmp/` bare Git и журналы репетиции, отзывает временное membership или доступ
app- и worker-login и выполняет предусмотренную ограниченную очистку
shadow-данных.
Очистка выводит только количества.

Параметр cleanup batch limit применяется отдельно к run, сообщениям и потокам,
а не ко всему окну суммарно. Для `N` одноходовых сценариев один проход должен
иметь лимит не меньше `2 × N`, потому что каждому сценарию соответствуют два
сообщения. При меньшем лимите оператор выполняет следующие ограниченные
проходы после проверки остаточных бесконтентных количеств и считает очистку
завершённой только при нуле run, metric и активных текстовых байтов.

Если процесс остановился после enqueue, но до terminal result, cleanup не
редактирует таблицы вручную. Отсутствующий или ещё `ready` отчёт сначала
становится бесконтентным `hard_stopped`; cleanup не вызывает смысловой
`run-next`. App-role inspection по `clock_timestamp()` может
предварительно пометить три безопасных случая: истёк retention до вызова,
истёкшая аренда `leased` при единственной попытке или истёкший
`calling_model`. Затем evaluator запускает отдельную credential-free
recovery-команду поверх того же exact-target `worker_claim`. Команда не
получает ключи Portal/Z.AI и фиксирует только terminal housekeeping. Если из-за
сдвига часов target неожиданно снова допускает аренду, транзакция claim
откатывается и cleanup остаётся незапущенным. После безопасного claim evaluator
всё равно требует ровно terminal outcome и одну бесконтентную metric.

Не удаляются рабочий Git, Stage 1, производственная база, wiki, секреты или
данные других прогонов. Отдельная база удаляется оператором по обычной
процедуре после проверки связанных запусков; команды с секретами здесь не
приводятся.

## Критерии готовности

Репетиция подготовлена, но не активирована, когда preflight и run выполнены в
закрытом режиме, локальный gateway вернул `no_change`, точный retry дал
идемпотентный результат, Git остался неизменным, внешний вызов не выполнялся,
а вывод не содержит содержимого и секретов. Отчёт хранит только команды,
статусы и количества.

Этот результат разрешает лишь запрос на отдельное одобрение реального
непроизводственного shadow-прогона и не является таким одобрением.

## Фактический первый реальный прогон

PM 2026-08-11 отдельно одобрил один непроизводственный прогон, определил его
как pet-test, выбрал Coding Plan и подтвердил разработчика `abc` владельцем
`Antarctica`. Это решение не меняет синтетический характер команд выше и не
является повторно используемым разрешением для production, SaaS или публичного
контура.

Оператор подготовил одноразовые PostgreSQL 17 database/login, HMAC-ключи,
Portal/Editor env и read-only bare Git. Реальный HTTP preflight доказал `401`
без корректного JWT и `200 allow` только после повторной серверной проверки
роли и владельца. Один диалог прошёл через локального помощника Editor и Z.AI:
основной SSE-ответ сохранил статус `200`, shadow завершился `no_change`, а Git
не изменился.

После 60-секундного срока cleanup удалил run и metric, заменил оба точных
сообщения tombstone-записями и оставил ноль активных байтов текста. Затем
временные база, runtime-role, ключи и bare Git были удалены. В отчёте сохранены
только статусы, количества, задержка и признаки неизменности; тексты, bearer,
ключи, строки подключения и содержимое wiki не сохранялись.

Прогон выявил и закрыл два операционных дефекта: автоматически добавленный
Strapi role-permission scope блокировал маршрут до Portal-контроллера, а
cleanup CLI использовал неподдерживаемый strip-only запуск TypeScript. JWT и
предметные проверки Portal не отключались; cleanup переведён на отдельный
`vite-node` wrapper. Следующий реальный прогон требует нового явного решения и
повторной подготовки всех операторских ворот.

## Фактическая первая попытка смысловой оценки

PM поручил продолжить Stage 2, что было применено как разрешение одного
пятисценарного Coding Plan окна в прежнем непроизводственном pet-test контуре
`abc → Antarctica`. Первые три отрицательные категории завершили coordinator:
их terminal result и metric были атомарно сохранены в одноразовой PostgreSQL.
Однако временный evaluator дополнял постоянную бесконтентную сводку только
после всей матрицы, поэтому после hard stop и удаления базы фактические
`no_change/proposal` исходы этих трёх случаев недоступны. Первый положительный
сценарий завершился безопасным отказом координатора; пятый вызов не выполнялся.

Сырые ответы provider по проектному правилу не журналировались, поэтому после
удаления одноразовой базы нельзя достоверно выбрать между malformed payload,
HTTP/quota, timeout и другими закрытыми причинами. Этот недостаток отчёта не
ослабляет безопасность, но означает, что окно не доказало смысловое качество.
Статический Sol high разбор обнаружил отдельный воспроизводимый пробел в
инструкции модели: она не описывала полный формат новой Markdown-страницы,
выбор новой страницы для нового предмета, запрет полной замены файла и
сохранение старого происхождения при локальной правке.

Исправление ограничено prompt существующего Z.AI adapter и regression-тестами
валидного создания и локального update. Серверная JSON Schema, нормализация,
проверки происхождения, `cubica_id`, области и exact anchors не ослаблены.
Повторный внешний вызов не входит в исправление: для него оператор снова
получает явное разрешение, подготавливает одноразовый контур и заново запускает
всю неизменную пятисценарную матрицу без промежуточной настройки prompt.
После каждого завершённого сценария evaluator должен до следующего вызова
дополнять отдельный постоянный бесконтентный отчёт, не перенося в него тексты,
пути, ссылки или содержимое кандидата. Runtime terminal result + metric
по-прежнему атомарно сохраняются существующим coordinator в одноразовой базе.

После отказа одноразовые shadow database/login/roles, точные сообщения, ключи,
bearer, копия Portal-базы и bare Git удалены; временный Portal остановлен.
Исходная Portal-база, канон и рабочий Git не изменялись.

## Фактическая повторная попытка смысловой оценки

PM 2026-08-11 явно разрешил новое неизменное пятисценарное Coding Plan окно.
Перед первым вызовом одноразовый evaluator синтетически подтвердил атомарную
запись, `fsync`, повторное чтение, строгий набор бесконтентных полей и права
`0600`. После каждого вызова он сохранял отдельный результат до решения о
следующем вызове.

Первый сценарий переходной беседы и второй сценарий уже известного факта дали
ожидаемый `no_change` за 3990 и 3536 мс. Третий сценарий неподтверждённого
предложения агента не дал смыслового результата: шлюз достиг фиксированного
15-секундного лимита и coordinator атомарно завершил run с
`gateway_timeout`. Это транспортный отказ, а не подтверждение или опровержение
правильности семантической классификации. В соответствии с hard-stop правилом
повтора не было, а сценарии нового решения и коррекции не запускались.

Постоянный бесконтентный отчёт сохранил точные исходы всех трёх выполненных
сценариев, число операций, задержку, объём и неизменность Git; тексты, пути,
ссылки, идентификаторы, сырые ответы и кандидаты в него не попадали. После
двухминутного срока хранения cleanup удалил 3 run и 3 metric, обезличил 6
сообщений и 3 потока и оставил 0 активных текстовых байтов. Затем временные
Portal, PostgreSQL database/login, HMAC/JWT, копия Portal-базы и bare Git были
удалены. Исходная Portal-база, канон и рабочий Git не менялись.

Окно не принимается: требуемая матрица `no_change, no_change, no_change,
proposal, proposal` не завершена. Один сетевой timeout не является основанием
менять prompt, ослаблять серверную проверку или повышать лимит автоматически.
Новая попытка требует отдельного явного разрешения и повторной подготовки всех
операторских ворот; Stage 3, активное чтение и Git-запись по-прежнему запрещены.

разрешение на одно окно с теми же границами и прежним лимитом модели 15 секунд.
Одноразовый evaluator и все операторские ворота были заново подготовлены и
проверены до первого внешнего вызова.

Все три отрицательных сценария впервые завершили полную отрицательную матрицу
с ожидаемым `no_change`: 8549, 3344 и 5244 мс. Первый положительный сценарий
снова не дал смыслового результата и завершился `gateway_timeout` за 15011 мс.
По hard-stop правилу повтор и сценарий коррекции не выполнялись. Prompt,

Одноразовые Portal, PostgreSQL database/login, HMAC/JWT, Portal-копия и bare

Окно не принимается: отрицательная классификация доказана, но полный путь

результате. Параметры не стали default; описанное здесь разрешение позднее
было израсходовано окном DR-13 2026-08-23.

## Фактическая четвёртая попытка смысловой оценки

PM разрешил ровно одно новое полное окно с лимитом модели 25 секунд,
coordinator lease 40 секунд, полным пределом процесса 50 секунд и без retry.
До первого внешнего вызова одноразовый evaluator подтвердил эти значения,
атомарную запись бесконтентного отчёта, `fsync`, повторное чтение и права
`0600`. Найденный в evaluator пропущенный `await` был исправлен до обращения к
provider, записи в PostgreSQL или создания сценарного артефакта; после этого
preflight и одноразовый контур были подготовлены заново.

Три отрицательных сценария дали ожидаемые `no_change` за 3352, 9337 и 9168 мс.
Создание нового долговременного знания дало одноперационный `proposal` за
13481 мс. Независимая Sol high проверка подтвердила только заявленные факты,
правильную страницу, минимальное локальное изменение и отсутствие дубликата,
противоречия или побочного переписывания. Сценарий коррекции существующего
знания не дал смыслового результата и завершился `gateway_timeout` за 25015
мс. Повтора и следующих внешних вызовов не было; prompt, валидаторы и Git HEAD
оставались неизменными.

Первый cleanup-проход выявил дефект только временного evaluator: число
сценариев `5` было передано как batch limit, хотя функция применяет лимит
отдельно к каждой таблице и сообщений было `10`. После установления причины
второй ограниченный проход той же штатной cleanup-функции завершил очистку, а
бесконтентный отчёт сохранил суммарный результат: удалены 5 run и 5 metric,
обезличены 10 сообщений и 5 потоков, осталось 0 активных текстовых байтов.
Одноразовые Portal, PostgreSQL database/login, HMAC/JWT, Portal-копия, bare Git
и evaluator удалены; канон, исходная Portal-база и рабочий Git не менялись.

Окно не принимается как полная матрица: доказаны все три отрицательных пути и
один положительный путь создания знания, но не путь коррекции. Разовое
разрешение 25 секунд израсходовано. Следующий внешний вызов требует нового
решения PM и предварительного выбора дальнейшего provider-пути; повышать лимит,
подстраивать prompt или запускать только пятый сценарий нельзя. Stage 3,
активное чтение, применение кандидатов и Git-запись остаются закрытыми.

## Фактическое окно DR-13 2026-08-23

После локальной проверки и Sol-high preactivation `ACCEPT` был подготовлен
новый disposable contour: PostgreSQL 17 с отдельными app/worker LOGIN,
loopback Strapi с положительной и отрицательной HTTP-авторизацией, HMAC worker
reauthorization и read-only bare Git. Maintained report был связан с точными
байтами manifest до первого enqueue.

Выполнено ровно четыре provider call без retry. Три отрицательных категории
вернули `no_change` и каждая прошла ручную рубрику 4/4. Четвёртая категория —
явно утверждённое новое долговременное знание — завершилась terminal
`gateway_malformed`; raw provider payload и candidate по принятой границе не
хранились. Hard stop исключил пятый сценарий, отдельный correction-only вызов
и применение результата. Git HEAD не менялся.

После retention credential-free cleanup удалил 4 run и 4 metric, обезличил 8
сообщений и 4 thread. Итоговый отчёт подтвердил нулевые active
runs/metrics/messages/threads/text bytes, `cleanup.passed=true` и неизменный
Git; manifest удалён. Затем уничтожены disposable PostgreSQL, Portal, bare Git,
LOGIN-роли и ключи.

Окно DR-13 израсходовано и не принимается как полная матрица. Maintained
evaluator теперь сохраняет существующий `schema_error`, не сворачивая его в
общий `mismatch`. DR-15 позднее добавил локальную allowlisted классификацию
этапа в существующий `last_error_code`, не изменяя report/metric. Новый внешний
вызов всё равно запрещён до отдельного явного решения. Stage 3 остаётся закрыт.

DR-16 не доказывает полную матрицу и не разрешает Stage 3. Следующий внешний

результата; настраивать prompt или повторять второй сценарий задним числом
