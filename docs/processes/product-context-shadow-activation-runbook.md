# Product Context Shadow: синтетическая репетиция активации

Репетиция проверяет только закрытый CLI-контур теневого запуска до любого
согласования реального shadow-прогона.

## Цель и границы

Используются фиксированные синтетические сообщения, локальный шлюз,
возвращающий `no_change`, и одноразовый bare Git в `.tmp/`, открытый только
для чтения. PostgreSQL — отдельная shadow-база с непривилегированным
runtime-login; миграция и membership роли подготавливаются оператором.

Репетиция не включает `PKS_KEY`, Z.AI или сеть, запуск Portal/Editor,
реальный bearer, пользователя, игру или wiki, применение миграции, cron,
секреты или TLS, а также записи в канон, Stage 1 или рабочий Git.

## Что готовит оператор

Оператор подготавливает изолированную shadow PostgreSQL и проверяет, что
runtime-login подключается только через loopback и имеет только заранее подготовленное membership в
`product_context_shadow_app`. Секреты, логины и адреса не записываются в
отчёты и команды примеров.

Также оператор создаёт временный bare Git под `.tmp/`, оставляет его без
изменений и предоставляет CLI read-only путь к нему. В репозитории нет
пользовательских, проектных или секретных данных.

## Автоматические проверки

Команды уже включают обязательные защитные флаги; дополнительные аргументы
передавать не нужно:

1. `npm run preflight:shadow:synthetic --workspace @cubica/product-context`;
2. после успешного preflight —
   `npm run run:shadow:synthetic --workspace @cubica/product-context`.

Preflight подтверждает test/staging, непривилегированный runtime-login,
подготовленную схему/роль и возможность открыть временный bare Git только для
чтения. Run использует встроенные фиксированные сообщения и локальный
`no_change` gateway, выполняет один shadow-run и его точный повтор с тем же
устойчивым ключом, после чего подтверждает идемпотентность и неизменность Git.
Код не читает provider credentials и не создаёт сетевой gateway.

Ожидаемый вывод содержит только `ready`, `no_change`, признаки точного повтора,
число локальных вызовов gateway и признак неизменности Git. Тексты, содержимое
wiki, адреса баз и репозиториев, bearer и секреты в выводе запрещены.

## Операторские ворота активации

Зелёный preflight не разрешает реальный shadow. Оператор отдельно подтверждает
отдельную базу и runtime-login с membership роли, test/staging, доверенный
origin и раздельные HMAC-ключи, серверный read-only bare Git с разрешённой
ревизией, разрешающую политику provider, одного разработчика и одну игру,
ограниченный объём и план хранения/удаления. В репетиции должны отсутствовать
`PKS_KEY`, реальный bearer и реальные тексты.

Каждый пункт получает отметку подтверждён, отклонён или не проверен. До
подтверждения всех пунктов режим остаётся выключенным.

## Отказ и повтор

Несоответствие preflight, внешний флаг, сетевой вызов, запись в Git,
неожиданный bearer или содержательный вывод означает отказ с кодом ошибки.
Отказ закрывает run и не меняет основной ответ, канон или Stage 1.

Точный повтор, доказывающий идемпотентность, выполняется внутри одной команды
`run`. После отказа оператор сначала выясняет, успел ли запуск записать
состояние. Неизвестный результат оборванного запуска не считается успехом, а
команду нельзя слепо перезапускать на той же базе. Неустранённый отказ
передаётся оператору без обхода проверки.

## Откат и очистка

При отказе оператор выключает synthetic-run, удаляет только созданные в
`.tmp/` bare Git и журналы репетиции, отзывает временное membership или доступ
runtime-login и выполняет предусмотренную ограниченную очистку shadow-данных.
Очистка выводит только количества.

Не удаляются рабочий Git, Stage 1, производственная база, wiki, секреты или
данные других прогонов. Отдельная база удаляется оператором по обычной
процедуре после проверки связанных запусков; команды с секретами здесь не
приводятся.

## Критерии готовности

Репетиция подготовлена, но не активирована, когда preflight и run выполнены в
закрытом режиме, локальный gateway вернул `no_change`, точный retry дал
идемпотентный результат, Git остался неизменным, внешний вызов не выполнялся,
а вывод не содержит содержимого и секретов. Отчёт хранит только команды,
статусы и количества.

Этот результат разрешает лишь запрос на отдельное одобрение реального
непроизводственного shadow-прогона и не является таким одобрением.

## Фактический первый реальный прогон

PM 2026-08-11 отдельно одобрил один непроизводственный прогон, определил его
как pet-test, выбрал Coding Plan и подтвердил разработчика `abc` владельцем
`Antarctica`. Это решение не меняет синтетический характер команд выше и не
является повторно используемым разрешением для production, SaaS или публичного
контура.

Оператор подготовил одноразовые PostgreSQL 17 database/login, HMAC-ключи,
Portal/Editor env и read-only bare Git. Реальный HTTP preflight доказал `401`
без корректного JWT и `200 allow` только после повторной серверной проверки
роли и владельца. Один диалог прошёл через локального помощника Editor и Z.AI:
основной SSE-ответ сохранил статус `200`, shadow завершился `no_change`, а Git
не изменился.

После 60-секундного срока cleanup удалил run и metric, заменил оба точных
сообщения tombstone-записями и оставил ноль активных байтов текста. Затем
временные база, runtime-role, ключи и bare Git были удалены. В отчёте сохранены
только статусы, количества, задержка и признаки неизменности; тексты, bearer,
ключи, строки подключения и содержимое wiki не сохранялись.

Прогон выявил и закрыл два операционных дефекта: автоматически добавленный
Strapi role-permission scope блокировал маршрут до Portal-контроллера, а
cleanup CLI использовал неподдерживаемый strip-only запуск TypeScript. JWT и
предметные проверки Portal не отключались; cleanup переведён на отдельный
`vite-node` wrapper. Следующий реальный прогон требует нового явного решения и
повторной подготовки всех операторских ворот.
