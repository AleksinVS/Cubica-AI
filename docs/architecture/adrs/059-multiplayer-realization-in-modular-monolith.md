## 1. Контекст

Модель мультиплеера принята в ADR-011 (free-form, последовательная обработка,
версионность `state_version`, broadcast через View Adapters) и хранение сессий —
в ADR-005 (PostgreSQL, JSONB, блокировки). Ранний текст ADR-011 называл
`session_events` очередью; принятая реализация уточняет, что это журнал только
подтверждённых фактов, а не транспорт ожидающих команд. Оба ADR писались под
целевую распределённую архитектуру (Router / Game Engine / Web Gateway),
которая по ADR-017 отложена: канонический backend — модульный монолит
`services/runtime-api`.

Фактическое состояние на 2026-07-05:

- сессии хранятся в `InMemorySessionStore` (зарегистрированный долг, `TSK-20260518-session-persistence-hardening`);
- сессия создаётся с одним необязательным `playerId`; модели «участники сессии» нет;
- стриминга обновлений в `runtime-api` нет — клиент получает состояние ответом на своё действие;
- принятый пакет возможностей пошаговых игр (ADR-058, позднее уточнённый
  ADR-084) вводит состояние «на игрока» и turn flow, но сам по себе не решает,
  **откуда** берётся аутентичный actor в сетевой игре.

Нужны решения, которых нет в ADR-011: как монолит последовательно принимает
команды, как игроки подключаются к сессии и получают идентичность, каким
транспортом доставляются обновления, как строится персональная проекция
состояния.

## 2. Решение

### 2.1. Размещение: модуль монолита, без выделения сервисов

Мультиплеер реализуется внутри `services/runtime-api` (session module + delivery
module). Router/Web Gateway не выделяются (ADR-017); внешний контракт
документируется как current API по ADR-051. Текущая логическая схема:
аутентифицированная HTTP-команда → последовательное транзакционное применение
под блокировкой строки сессии → подтверждённый факт в `session_events` →
уведомление. Отдельные очередь и воркер для v1 не создаются.

### 2.2. Предусловие: PostgreSQL-хранилище сессий

До включения сетевого мультиплеера `InMemorySessionStore` заменяется PostgreSQL-хранилищем по ADR-005 (`game_sessions` + `state_version`, `last_event_sequence`). Таблица `session_events` хранит только подтверждённые неизменяемые игровые факты из транзакции команды. Если асинхронной доставке понадобится очередь до исполнения, она использует отдельную таблицу `session_command_queue`; ожидающая команда не называется событием и не смешивается с журналом. Однопользовательские игры и хотсит переходят на то же хранилище — одна модель персистентности для всех режимов.

### 2.3. Модель участников (participants) и подключение

- Сессия получает **места** (seats) по `config.players` манифеста: `session.participants = [{ seatId, playerId, kind: "human" | "agent", joinState }]`.
- `participants` — неизменяемые авторитетные метаданные сессии, а не часть
  игрового state и не декларация манифеста конкретной игры. Публичная форма:
  `seatId: string`, `playerId: string`, `kind: "human" | "agent"`,
  `joinState: "local" | "private-invite"`. Значение `private-invite` — ровно
  одна привязка сетевого участника к заранее назначенному месту, а не состояние
  присутствия или жизненного цикла. `pending`, `joined`, online/offline и иные
  изменяемые состояния подключения в метаданные участника не добавляются.
- `seatId` стабильно обозначает место сессии, а `playerId` — игровой actor. Для
  игры с материализованной player/turn-моделью он обязан однозначно ссылаться
  на ключ `state.players`; `public.turn.order` и `activePlayerId` используют те
  же `playerId`. Нейтральная неходовая сессия не получает искусственные
  `state.players` или `public.turn`: её actor остаётся неопределённым без
  отдельно ограниченного principal scope.
  Локальный materializer S8 использует `seatId === playerId`, но это не
  превращается в долговременное смысловое тождество двух идентификаторов.
- Идентичность игрока и места назначает runtime; клиент не выбирает свой
  `playerId`. В `private-invite` v1 runtime при создании сессии атомарно создаёт
  durable capability (долговечное право доступа, подтверждаемое владением
  секретом): host credential управляет только первым участником, а отдельный
  invite credential — ровно одним из остальных участников. Количество мест
  выводится из общего манифеста и не фиксируется контрактом под Estate Race или
  под два места.
- `POST /sessions` принимает необязательный `accessMode: "local" |
  "private-invite"`; отсутствие поля означает прежний `local`. Только прямой
  ответ создания доверенному BFF может вернуть host `credential` и
  `privateInvites: [{ credential }]`. Идентичность места не принимается из
  ссылки: runtime выводит её только из аутентифицированного principal.
  Последующие GET и ответы действий не содержат эти секреты. Capability
  действует до архивации сессии; runtime хранит только криптографический хеш
  секрета, а не исходное значение. Хост-браузер временно является поверхностью
  обработки гостевых секретов, пока показывает ссылки; закрытие панели удаляет
  их из состояния Presenter, а импорт переносит credential в HttpOnly cookie.
- В private network v1 нет отдельной таблицы invites, одноразового redemption,
  TTL, ротации или отзыва, публичных комнат, matchmaking, spectators и смешения
  agent + network. Ротация и отзыв обязательны к отдельному решению до
  публичного выпуска, поскольку утрата ссылки передаёт контроль над точным
  местом до архивации сессии.
- **Хотсит — вырожденный случай той же модели**: одно подключение владеет
  всеми местами (`joinState: "local"`) и получает стабильную идентичность
  principal контроллера сессии. Actor определяется runtime по правилам игры
  при первом принятии `commandId` и сохраняется в квитанции. В сетевой модели
  principal выводится из аутентифицированного участника соединения, после чего
  runtime отдельно проверяет, каким actor ему разрешено действовать.

Первое включение обязательного `participants` является явно разрушительным
pre-release cutover. Поддерживаемых production-сессий до S8 нет, поэтому
миграция удаляет прежние `game_sessions` и зависимые principals, receipts,
events и schedules по действующим каскадным связям, но сохраняет неизменяемые
`game_bundles`. Backfill из игрового state запрещён: он создал бы неявную
совместимость и риск ошибочной actor identity. Эта граница относится только к
переходу до первого production-запуска; будущие поддерживаемые сессии нельзя
удалять такой миграцией без отдельного решения и операционного подтверждения.

### 2.4. Последовательная обработка команд

- Текущий HTTP-путь обрабатывает команды **строго последовательно на сессию**
  внутри repository transaction под строковой блокировкой PostgreSQL
  `SELECT FOR UPDATE NOWAIT`. Будущий асинхронный транспорт может сначала
  записать аутентифицированный закрытый конверт команды в
  `session_command_queue`, после чего воркер монолита возьмёт его под той же
  блокировкой. Подтверждённые события появляются в `session_events` только
  вместе с состоянием и квитанцией после исполнения; статусов
  `pending/processing` у игрового факта нет.
- Каждый публичный `POST /actions` обязан передавать `commandId` и
  `expectedStateVersion` —
  версию снимка, на основании которого клиент выбрал действие. Runtime сравнивает
  версию с текущей **внутри той же исключительной блокировки сессии и до
  вызова игрового обработчика**, но только после поиска command receipt.
  Совпавший `commandId` возвращает прежний результат без повторного исполнения;
  новый `commandId` с устаревшей версией получает HTTP 409, не создаёт принятого
  игрового события, не применяет команду и не изменяет снимок; стабильный
  результат отказа сохраняется в command ledger.
- Конфликты — «кто успел первым»: проигравшая команда отклоняется проверкой с управляемой ошибкой (ADR-011 §2.6). Никакого слияния состояний.
- Таймауты `processing`, лимит попыток и архивация относятся только к будущей `session_command_queue`. Подтверждённый журнал `session_events` неизменяем.

### 2.5. Транспорт обновлений: SSE-уведомления в runtime-api

- `runtime-api` предоставляет аутентифицированный `GET
  /sessions/{sessionId}/events` с `Content-Type: text/event-stream`. Это
  односторонний Server-Sent Events (SSE) поток: команды по-прежнему приходят по
  HTTP, поэтому двусторонний WebSocket для v1 не нужен.
- Каждое событие несёт только закрытый schema-first payload
  `{ stateVersion, lastEventSequence }`. Состояние, персональная проекция,
  игровые события и дельты через SSE не передаются.
- Получив уведомление, клиент запрашивает существующий аутентифицированный
  `GET /sessions/{sessionId}` и получает полную актуальную персональную
  проекцию. Реконнект также всегда означает полную REST-ресинхронизацию; resume
  дельт и stream tickets в v1 отсутствуют.
- OpenAPI остаётся источником истины для endpoint и payload; TypeScript и
  исполняемые JSON Schema производятся действующим генератором в
  `packages/contracts/session`. Ограничения числа соединений, heartbeat,
  backpressure и отключение медленных клиентов — внутренние меры безопасной
  эксплуатации. Процесс допускает не более одного активного потока на
  `(sessionId, principalId)`, новый поток заменяет прежний, общий предел равен
  128, а исчерпание ёмкости выражено публичным HTTP 429.

### 2.6. Персональная проекция (playerView)

- Player-facing content boundary (ADR-019) расширяется параметром «наблюдатель» (`viewerPlayerId`): проекция включает `public`, собственную ветку `players.<viewer>` целиком, чужие ветки — только по правилам видимости `playersTemplate.visibility` (ADR-058 §2.3); `secret` и скрытые порядки колод не покидают runtime никогда.
- Один и тот же строитель проекции обслуживает REST-ответы и (в ADR-060)
  проекцию для агента-игрока — это единственная точка фильтрации секретов. SSE
  не строит вторую проекцию и только предлагает клиенту перечитать REST view.

## 3. Отклонённые альтернативы

1. **Выделение Router/Web Gateway в отдельные сервисы сейчас.** Отклонено ADR-017: операционные границы не подтверждены; модель ADR-011 полностью реализуема в монолите.
2. **Сторонний realtime-фреймворк (Colyseus, PartyKit и т.п.).** Отклонено: вводит второго владельца игрового состояния и собственную модель комнат, конфликтуя с ADR-018/ADR-019 (state ownership у runtime-api) и контрактной дисциплиной ADR-051.
3. **CRDT/OT-слияние одновременных действий.** Отклонено ADR-011 §2.6: для пошаговых и free-form игр достаточно последовательной очереди и guard-отклонений.
4. **Long-polling как основной транспорт.** Отклонено: пошаговым играм нужны своевременные уведомления «твой ход»; polling допустим только как деградация клиента, не как контракт.
5. **Клиентский выбор собственного playerId.** Отклонено: идентичность —
   атрибут заранее назначенного runtime места, доступ к которому доказывается
   соответствующей capability; иначе невозможна честная адресация `{{actor}}`.
6. **Отдельная модель хранения для мультиплеера (память для single, БД для multi).** Отклонено: двойная персистентность — источник расхождений; долг `InMemorySessionStore` и так подлежит снятию.
7. **Считать проверку версии достаточной защитой от повтора.** Отклонено
   уточнением ADR-084: после потерянного успешного ответа версия уже изменилась,
   поэтому без command ledger клиент не отличит выполненную команду от
   конфликта. Ledger хранится транзакционно вместе с изменением сессии.
8. **Одноразовое поглощение invite и отдельная таблица приглашений.** Отклонено
   для private network v1: оно добавляет новый жизненный цикл и хранилище без
   пользы для закрытого запуска. До публичного выпуска граница должна быть
   пересмотрена вместе с ротацией и отзывом.
9. **WebSocket для уведомлений v1.** Заменён односторонним SSE: команды уже
   используют HTTP, а минимальное уведомление не требует двустороннего канала.

## 4. Последствия

### Положительные

- ADR-011/ADR-005 получают реализуемый план в текущей архитектуре без ревизии самих решений.
- Единая модель участников покрывает хотсит, сетевую игру и агентские места (ADR-060) — игровые манифесты не меняются между режимами.
- Единственная точка фильтрации секретов снижает риск утечки чужого состояния.
- Потерянный ответ и повторная отправка оплаты, карты или движения больше не
  приводят к двойному применению: `commandId` возвращает исходную квитанцию, а
  версия разрешает только конкуренцию разных команд.

### Отрицательные / риски

- Монолит удерживает долгоживущие SSE-соединения: рестарт процесса рвёт поток,
  но клиент восстанавливает его через полную REST-ресинхронизацию без отдельного
  состояния доставки или stream ticket.
- Потеря durable capability link передаёт контроль над привязанным местом до
  архивации сессии; это осознанный риск закрытого v1, а ротация и отзыв являются
  обязательной отложенной границей перед публичным выпуском.
- Появляется эксплуатационная зависимость от PostgreSQL уже в MVP-контуре (миграции, бэкапы).
- Строковая блокировка `SELECT FOR UPDATE NOWAIT` допускает только одну
  изменяющую HTTP-транзакцию на сессию; конкурирующая команда получает
  управляемый отказ. Для настольных игр это осознанная граница, а отдельные
  очередь и воркер остаются будущим решением.
- Клиент обязан хранить последнюю подтверждённую `stateVersion` и незавершённый
  `commandId`. После HTTP 409 новый игровой выбор требует ресинхронизации;
  транспортный retry той же команды безопасно использует прежний `commandId`.
