## 1. Понимание решения

Решение понято так: автор работает с визуальным предпросмотром игры, а не с
файлами или техническим diff. ИИ может только подготовить ограниченный
`EditorChangeSet`. Редактор строит из него точный временный предпросмотр, после
чего пользователь либо применяет именно показанный результат, либо отменяет
его. Прямые пользовательские действия Save, Undo и Redo не являются
инструментами ИИ и не требуют agent approval envelope.

Технические пути файлов, before/after hashes и effect digest нужны серверу для
целостности и конкурентной проверки, но не являются пользовательским
представлением изменения.

## 2. Контекст

Текущий `/api/editor/apply` принимает готовые полные тексты sibling-документов,
доверяет клиентскому dry-run, не использует общую аренду мутаций и изменяет
активный документ отдельно в браузере. Поэтому одна логическая операция может
расходиться между предпросмотром, активным документом и рабочей копией.

Старый Agent UI дополнительно публикует `apply`, `undo` и `save` как вызываемые
моделью mutating tools. Их approval scope не описывает полный фактический
эффект, а расширение approval ledger для локального однопользовательского
редактора добавило бы постоянное состояние без продуктовой необходимости.

## 3. Решение

1. **Schema-first контракт.** Каноническая форма `EditorChangeSet`, запросов
   prepare/confirm и ответов задаётся
   `docs/architecture/schemas/editor-mutation.schema.json`. TypeScript-типы
   являются генерируемой проекцией схемы.
2. **Один серверный расчёт.** Общая чистая функция загружает документы активной
   editor-сессии, сверяет SHA-256 текущей дисковой версии активного документа,
   подставляет его текущий проверяемый browser buffer, выполняет schema и
   semantic dry-run для каждого затронутого документа, классифицирует риск и
   строит нормализованный эффект.
3. **Точный временный предпросмотр.** Prepare выполняется под существующей
   session mutation lease. Компилятор получает подготовленные after-тексты как
   временные входные overrides и публикует только производные runtime-артефакты
   предпросмотра. Authoring-файлы до подтверждения не записываются.
4. **Внутренняя привязка.** Сервер возвращает domain-separated SHA-256 от
   версии политики, identity сессии/игры/активного документа, нормализованного
   `EditorChangeSet`, риска и отсортированных before/after SHA-256 всех
   затронутых документов. Пользователь этот digest не видит.
5. **Подтверждение.** Кнопка «Применить» принадлежит Editor UI, а не
   декларативному agent tool. Confirm повторно выполняет тот же расчёт под той же
   арендой, сравнивает digest до первой записи и атомарно записывает все
   затронутые authoring-документы, включая активный. Несовпадение, устаревшая
   версия, ошибка валидации или no-op не записывают ничего.
6. **Локальный журнал после успеха.** Browser undo journal обновляется только
   после успешного confirm и использует подтверждённые сервером after-тексты и
   inverse ChangeSet. Undo, Redo и другие уже конкретные прямые действия UI
   используют тот же серверный расчёт и атомарную запись в одношаговом
   `direct`-режиме: второй preview им не нужен, потому что действие уже выбрал
   пользователь.
7. **Save остаётся Save.** Save — отдельное явное пользовательское действие,
   которое создаёт долговечную Git-версию по ADR-075. Оно не является
   AI-инструментом и не входит в effect digest отдельного `EditorChangeSet`.
8. **Layout остаётся отдельным sidecar.** Его запись не проводится через
   `EditorChangeSet`, но требует непустые `sessionId` и `versionHash`, точную
   session worktree и общую session mutation lease.
9. **Agent surface только предлагает.** Из каталога и адаптеров помощника
   удаляются `editor.applyChangeSet`, `editor.undoLastPatch`,
   `editor.saveSession` и ставший ненужным `editor.requestHumanApproval`.
   Планирование, dry-run, подготовка прототипа и предпросмотра остаются
   неавторитетными операциями.

## 4. Инварианты

- Ни один результат модели или аргумент tool call не подтверждает изменение.
- Видимая пользователю версия кандидата и подтверждаемый digest происходят из
  одного серверного подготовленного эффекта.
- Между prepare и confirm не удерживается аренда; confirm обязан перечитать
  состояние и безопасно отклонить устаревший эффект.
- Сервер не принимает готовые after-тексты как команду записи: он принимает
  `EditorChangeSet` и сам повторно вычисляет итоговые документы.
- Атомарный batch включает активный и sibling-документы. Ошибка записи
  восстанавливает исходные байты уже затронутых файлов.
- Производные runtime-артефакты временного preview не являются authoring
  source of truth и не входят в обычный Save.
- Отсутствие активной editor-сессии или session worktree закрывает apply и
  layout fail closed.

## 5. Упрощения и отложенные возможности

Принят минимальный вариант без нового сервиса, базы данных, очереди, CRDT,
временной Git-ветки, удержания аренды между запросами, клиентской
криптографии и постоянного approval ledger. Effect digest не является
самостоятельным доказательством личности пользователя; он доказывает только
тождество подготовленного и повторно вычисленного эффекта внутри текущей
границы Editor UI/session.

Hosted multi-user authoring потребует отдельного решения об аутентификации,
авторизации и серверном журнале подтверждений. Такое решение не включается в
исправление F-004/F-010 и не имитируется локальным реестром.

## 6. Последствия

Положительные:

- пользователь подтверждает визуально показанный результат, а не файл или
  технический diff;
- модель больше не получает вызываемых инструментов записи, Save или Undo;
- preview и confirm используют один расчёт, а stale/substitution завершаются
  без частичной записи;
- уже существующие session lease, compiler, worktree и browser journal
  переиспользуются.

Ограничения:

- подготовка визуального кандидата компилирует производные артефакты и поэтому
  дороже локального текстового dry-run;
- безопасность hosted-сценария по-прежнему зависит от будущей полноценной
  identity/authorization границы ADR-065.

## 7. Проверка

- контракт валидируется стандартным JSON Schema validator, а generated types
  проверяются на drift;
- route-тесты доказывают lease, stale before-hash, digest substitution, no-op,
  server validation и полное отсутствие записи при ошибке;
- repository-тест доказывает rollback всего batch, включая активный документ;
- UI-тест доказывает, что agent plan только создаёт preview-кандидат, а запись
  происходит лишь по прямой кнопке «Применить»;
- каталоги и адаптеры Agent UI не публикуют mutating Editor tools;
- layout-тесты доказывают обязательные session, versionHash и lease.
