# ADR-104: Проверяемый ИИ-черновик итогового разбора для ведущего

- **Дата:** 2026-08-27
**Status:** Accepted
- **Решение PM:** первый поставщик — Z.AI, модель `glm-4.7`; на текущем
  этапе внешняя обработка может получать любые данные сессии; хранится один
  черновик на срок жизни сессии и полный аудит без повторной копии журнала
- **Компоненты:** session contracts, Runtime API, PostgreSQL, Player Web,
  игровые пакеты
- **Связанные решения:** ADR-005, ADR-045, ADR-046, ADR-047, ADR-071,
  ADR-084, ADR-103

## 1. Как понято решение

Cubica создаёт для ведущего один проверяемый ИИ-черновик итогового разбора
сессии. Он является производным документом поверх уже подтверждённого журнала и
закреплённой версии игры, не меняет игровое состояние и не становится скрытой
оценкой участников. Первый потребитель — «Карты, деньги, поезда», но серверная
граница и контракт не содержат идентификатора или правил этой игры.

## 2. Контекст

ADR-103 уже предоставляет полный переносимый журнал подтверждённых публичных
событий с точной границей последовательности. Существующий Agent Turn выбирает
Game Intent и может привести к игровой транзакции; использовать его для
итогового разбора означало бы дать производной аналитике ненужную мутационную
границу. Cubica Surface предусматривает будущую поверхность
`facilitator.debriefDraft`, но первый срез не обязан вводить генерируемую
поверхность: стабильный типизированный документ безопаснее отрисовать обычным
компонентом Player Web.

## 3. Решение

1. Runtime API получает отдельный facilitator-only путь чтения и запуска
   разбора. Он не является Gameplay Action, Agent Turn или Mechanics-планом.
2. Запуск закрепляет точный снимок сессии, `bundleHash`, версию состояния и
   `throughEventSequence`, строит переносимый журнал и вызывает поставщика
   только после повторной проверки роли ведущего.
3. Первый поставщик фиксирован сервером: Z.AI Chat Completions, модель
   `glm-4.7`. Клиент не выбирает endpoint, модель, промпт или параметры.
4. Ответ модели принимается только как JSON и проверяется канонической JSON
   Schema и отдельными межполевыми инвариантами. Невалидный ответ не создаёт
   черновик.
5. Для одной сессии допускается ровно один успешно принятый черновик. Повторное
   чтение возвращает его без нового вызова модели. Неуспешные попытки остаются
   в аудите; новый явный запуск после ошибки допустим, автоматических повторов
   нет.
6. Черновик живёт столько же, сколько данные сессии. Удаление сессии удаляет
   черновик и связанные попытки тем же каскадом; архивирование не удаляет их.

## 4. Вход и происхождение

Модель получает ограниченный сервером конверт, содержащий:

- переносимый журнал ADR-103;
- нужную для объяснения публичную проекцию конечного состояния;
- закреплённые учебные цели и компетенции из неизменяемого игрового пакета;
- точные идентификаторы формата и версии входа без credential, API key и иных
  транспортных секретов.

Действующее решение PM разрешает при необходимости передавать поставщику любые
данные сессии. Первый срез всё равно отправляет только перечисленный полезный
минимум. Это не считается принятой долгосрочной политикой минимизации: отдельный
долг обязан определить классификацию данных, согласие, обезличивание,
территорию обработки и ограничения для следующих сред.

Точный сериализованный журнал не копируется в аудит. Runtime сохраняет его
SHA-256 и `throughEventSequence`; хеш считается по тем же UTF-8 байтам, которые
выдаёт канонический сериализатор ADR-103.

## 5. Выход и контроль ведущего

Черновик версии `1.0.0` разделяет:

- подтверждённые факты с одной или несколькими ссылками на номера событий;
- интерпретации с теми же доказательными ссылками и явной уверенностью;
- вопросы для групповой рефлексии;
- краткое резюме и предупреждение, что текст создан ИИ и требует проверки.

Факт без ссылки на событие отклоняется. Интерпретация не маркируется как факт.
Контракт запрещает психологические диагнозы, скрытые личностные оценки и
команды изменения игры. Ведущий видит документ как черновик, может скопировать
его для своей работы, но первая версия не вводит редактор, версии ручных правок
или автоматическую публикацию участникам.

## 6. Поставщик и отказоустойчивость

- Runtime вызывает фиксированный HTTPS endpoint Z.AI с `model = glm-4.7`,
  `response_format = json_object`, без инструментов, поиска, перенаправлений и
  потоковой выдачи.
- Reasoning-вывод не нужен для продукта; thinking отключён, чтобы не создавать
  неуправляемый второй корпус чувствительных данных.
- Размер входа, ответа, число выходных элементов и время запроса ограничены.
- Запрос выполняется синхронно по явному действию ведущего. Ошибка, timeout,
  квота или невалидный JSON возвращают безопасный статус и не блокируют
  завершение либо просмотр обычного журнала.
- Автоматический retry отсутствует. Ведущий может явно повторить только после
  сохранённой неуспешной попытки; успешно принятый черновик неизменяем.

## 7. Хранение и аудит

PostgreSQL хранит session-owned попытки и максимум один успешный результат.
Для in-memory режима действует та же семантика без долговечности процесса.
Аудит сохраняет всё содержательное, кроме повторной копии журнала и секретов:

- provider, endpoint profile, model и параметры генерации;
- версию и полный системный промпт, его SHA-256;
- входной снимок без байтов журнала, SHA-256 журнала, `bundleHash`, версии
  состояния и события;
- внутренний request/run id и доступный provider request id;
- времена, длительность, usage, HTTP-класс результата и классифицированную
  ошибку;
- ограниченные точные байты ответа поставщика и проверенный черновик.

Состав аудита намеренно является первым рабочим профилем, а не окончательной
политикой. Отдельный долг должен определить обязательные поля, срок хранения,
доступ, шифрование, удаление, экспорт и допустимость точных provider bytes.

## 8. Доступ и приватность

- Запуск и чтение доступны только аутентифицированному principal с ролью
  `facilitator`; браузерный credential остаётся в HttpOnly BFF.
- Черновик не входит в публичный журнал и не выдаётся обычному участнику.
- Provider credential существует только в серверной конфигурации, не
  сохраняется в аудите и не попадает в ответы или логи.
- Текущее широкое разрешение внешней обработки является осознанным временным
  риском, а не разрешением для публичного production без следующего решения о
  приватности.

## 9. Отклонённые варианты

- **Использовать Agent Turn.** Отклонено: его назначение — выбирать и исполнять
  Game Intent, тогда как разбор должен быть строго read-only.
- **Добавить отдельный сервис, очередь или векторную базу.** Отклонено: один
  пользовательский запрос и один документ не оправдывают новый операционный
  компонент.
- **Сохранять копию журнала вместе с разбором.** Отклонено: event ledger уже
  каноничен; хеш и граница последовательности дают точную связь без дублирования.
- **Хранить только свободный Markdown.** Отклонено: невозможно автоматически
  проверить разделение фактов и интерпретаций и ссылки на доказательства.
- **Автоматически публиковать результат командам.** Отклонено: модельный текст
  сначала должен быть видимым черновиком ведущего.

## 10. Последствия

- CMT получает первый полезный ИИ-инструмент поверх проверяемых игровых фактов.
- Провайдерная ошибка не влияет на игру, журнал или финальный расчёт.
- Runtime получает узкий read-only provider adapter, но не production Agent
  Runtime adapter; `LEGACY-0029` остаётся открытым для AI-driven игр.
- Следующие игры смогут включить тот же черновик без предметной ветки в Runtime,
  когда предоставят подходящие публичные события и учебные метаданные.
- До снятия новых долгов решение допускается для текущего этапа и закрытого
  тестирования, но не объявляет завершённой общую privacy/audit governance.
