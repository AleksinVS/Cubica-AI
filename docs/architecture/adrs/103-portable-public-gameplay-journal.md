# ADR-103: Переносимый журнал подтверждённых публичных событий

- **Дата:** 2026-08-12
**Status:** Accepted
- **Решение PM:** общий переносимый журнал принят; ИИ-интерпретация вынесена в последующие этапы

## 1. Как понято решение

Cubica получает общий для разных игр журнал, который можно выгрузить и прочитать
вне плеера. Он содержит только уже подтверждённые сервером события с аудиторией
`public`, остаётся только для чтения и не участвует в расчёте состояния, счёта или
доступности действий. ИИ-разбор, учебная рефлексия и оценка поведения участников
не входят в этот контракт и потребуют отдельного решения.

## 2. Контекст

Runtime уже хранит неизменяемую последовательность событий вместе с состоянием и
квитанцией команды. Игры могут дополнительно проецировать события в
`state.public.log` для своего интерфейса, но эта коллекция является удобным
игровым представлением, а не защищённым источником истины. Построение выгрузки из
неё закрепило бы разные форматы игр и позволило бы клиентской проекции расходиться
с фактически подтверждёнными событиями.

Защищённая запись события содержит также служебные идентификаторы команды,
квитанции и principal. Они нужны для внутреннего аудита и повторного исполнения,
но не должны автоматически становиться частью переносимого пользовательского
документа.

## 3. Решение

1. Источник журнала — неизменяемые записи `SessionEventRecord` с
   `audience = public`, сохранённые в одной транзакции с применённой командой.
2. Runtime API строит отдельную безопасную проекцию. В неё входят версия формата,
   идентификаторы игры и сессии, граница последовательности и упорядоченные
   публичные факты: стабильная ссылка события, его номер, тип, время, `summary`,
   `data` и необязательные изменения публичных метрик.
3. `principalId`, `commandId`, `receiptId`, защищённый Mechanics audit, закрытые
   события и секретное состояние в журнал не входят. Если игре нужен публичный
   участник или иная связь, она объявляет это в типизированном `data` публичного
   события.
4. Каноническая форма документа задаётся отдельной JSON Schema. Производный
   TypeScript-тип генерируется из схемы, а Runtime API проверяет выдаваемый
   документ стандартным валидатором и отдельными семантическими проверками
   порядка.
5. Плеер не собирает и не исправляет журнал. Он запрашивает готовый документ у
   Runtime API через credential-holding BFF и сохраняет полученные байты как JSON.
6. Первый вертикальный срез доказывается нейтральной серверной фикстурой и
   настоящей сессией «Карты, деньги, поезда» без ветки по идентификатору игры в
   общем коде.

## 4. Инварианты

- Журнал только для чтения: запрос не меняет state version, event sequence,
  квитанции, расписания или игровое состояние.
- Записи следуют строго по возрастанию защищённой `sequence`. Номера могут иметь
  пропуски, если между публичными фактами были события другой аудитории.
- `throughEventSequence` закрепляет точную серверную границу, относительно
  которой построен документ. Одновременная следующая команда не дописывается в
  уже сформированный ответ частично.
- Выгрузка не пересказывает игровые события и не локализует их заново: `summary`
  и `data` остаются подтверждёнными JSON-значениями игры.
- Изменение несовместимой формы требует новой версии схемы. Добавление ИИ-полей
  в этот документ запрещено: интерпретация должна быть отдельной производной со
  своей версией и происхождением.
- Пределы размера применяются с отказом, а не с молчаливым усечением: файл либо
  соответствует объявленной границе полностью, либо не выдаётся.
- Ограничение количества применяется уже при чтении event ledger: Runtime не
  материализует неограниченную историю до проверки предела ответа.

## 5. Граница доступа

Журнал не является общедоступной ссылкой. Для живой сессии его может прочитать
любой principal, уже аутентифицированный в этой сессии: данные всё равно имеют
аудиторию `public`. После архивирования действует более узкая существующая
граница архива — credential ведущего. Браузер не получает bearer credential:
его добавляет тот же серверный BFF, который обслуживает чтение сессии и действия.

## 6. Отклонённые варианты

- **Выгружать `state.public.log`.** Отклонено: это игровая UI-проекция с разной
  формой и ограничением коллекции, а не неизменяемая последовательность фактов.
- **Отдать защищённые `SessionEventRecord` целиком.** Отклонено: раскрывает
  служебные идентификаторы и связывает внешний формат с внутренним аудитом.
- **Собирать файл в браузере из снимков состояния.** Отклонено: клиент не видит
  защищённый порядок событий, может пропустить промежуточные команды и стал бы
  вторым источником истины.
- **Сразу добавить CSV, печатный отчёт и ИИ-комментарии.** Отклонено для первого
  среза: CSV теряет вложенные типизированные данные, а представление и
  интерпретация не должны расширять фактический контракт.
- **Завести отдельное хранилище журнала.** Отклонено: документ является
  детерминированной безопасной проекцией уже сохранённого event ledger.

## 7. Последствия

- Появляется переносимый межигровой документ, пригодный для независимой проверки
  и будущих производных инструментов.
- Сервер отвечает за удаление защищённых полей и полноту выгрузки; клиентская
  реализация остаётся простой и не знает семантику игры.
- Схема переносимого журнала становится первой schema-backed частью публичных
  session contracts. Общий долг перевода остальных session-контрактов на
  schema-first остаётся отдельным.
- Большие журналы требуют контролируемого предела ответа; будущая постраничная
  доставка может быть добавлена совместимо, не меняя документ версии `1.0.0`.
