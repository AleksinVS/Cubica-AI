# ADR-104: Проверяемый ИИ-разбор подтверждённой истории сессии

- **Дата:** 2026-09-04
**Status:** Accepted
- **Решение PM:** принят отдельный read-only ИИ-артефакт с OpenAI Responses API,
  ограниченным внешним контуром и подтверждением ведущего
- **Компоненты:** AI contracts, session contracts, runtime API, Player Web,
  игровые пакеты, PostgreSQL
- **Связанные решения:** ADR-043, ADR-047, ADR-051, ADR-071, ADR-084, ADR-101,
  ADR-103

## 1. Как понято решение

Cubica получает общую границу для проверяемого ИИ-разбора уже состоявшейся
игровой сессии. Разбор только читает точную версию переносимого публичного
журнала и опубликованную методику игры, не является Agent Turn и не изменяет
игровое состояние. Полученный документ остаётся черновиком до явного
подтверждения ведущим и даже после подтверждения не становится источником
истины игровых фактов.

Первый продуктовый срез использует «Карты, деньги, поезда», а первый внешний
адаптер — OpenAI Responses API. Общий runtime знает только нейтральный контракт
и опубликованный профиль разбора, но не содержит веток или терминов CMT.

## 2. Контекст

ADR-103 закрепил переносимый журнал как безопасную schema-backed проекцию
подтверждённых публичных событий. Добавление в него выводов модели смешало бы
наблюдаемые факты с вероятностной интерпретацией и лишило бы журнал свойства
проверяемого документа.

Существующий Agent Turn решает другую задачу: модель выбирает Game Intent,
который проходит изменяющую command transaction. Итоговый разбор не выбирает
действие и не должен получать доступ к защищённому аудиту, секретному состоянию
или правам на изменение сессии. Нужны отдельные контракт, доступ, хранение,
идемпотентность и контроль внешней передачи данных.

## 3. Решение

1. Вводится нейтральный schema-first контракт производного ИИ-артефакта
   сессии. Он отделён от переносимого журнала, Agent Turn, состояния сессии,
   событий и квитанций команд.
2. Вход формируется сервером из полной точной версии переносимого публичного
   журнала и опубликованного game-owned профиля методики. Свободные заметки,
   защищённый аудит и секретное состояние не являются допустимыми источниками.
3. Ответ разделяет подтверждаемые факты со ссылками на события,
   интерпретации и вопросы ведущему. Сервер проверяет форму стандартным
   JSON Schema-валидатором, а ссылки и межполевые инварианты — отдельной
   смысловой проверкой.
4. Генерация выполняется одним синхронным server-only обращением без
   инструментов, встроенного поиска и долговременной беседы поставщика.
   Молчаливое усечение входа, автоматический fallback и автоматический повтор
   после неизвестного результата запрещены.
5. Первый адаптер использует OpenAI Responses API с `store: false`, строгим
   структурированным ответом, закреплённым снимком модели и версионированным
   промтом. Конкретный снимок допускается к трафику только после replay/eval
   проверки; допуск связывает точную модель, канонический профиль методики,
   собранный текст инструкций и eval-корпус их SHA-256 отпечатками. Изменяемый
   alias не считается закреплённой моделью.
6. Запрос, происхождение, ограниченная копия структурированного ответа, расход,
   классифицированный результат и решение ведущего хранятся отдельно в
   PostgreSQL. Это единственный долговечный источник ИИ-артефакта; provider-side
   storage, session state, event ledger и command receipts им не являются.
   Каноническая входная строка сохраняется без преобразования и одновременно
   является источником `input_sha256` и телом, передаваемым поставщику; JSONB —
   только удобная инспекционная копия.
7. Для ограниченной предпроизводственной проверки модели допускается отдельный
   вручную запускаемый адаптер Z.AI `glm-5.3-flash`. Он использует только закреплённую
   синтетическую CMT-фикстуру, Chat Completions JSON mode и локальную строгую
   проверку той же JSON Schema. Сам адаптер до сетевого вызова сверяет SHA-256
   полного канонического входа с утверждённой фикстурой. Он не внедряется в
   runtime-сервис, не создаёт долговечный артефакт и не разрешает передачу
   реального журнала. Для ручного proof из официально поддерживаемого Codex
   допускается явно заданный Coding Plan base URL; адаптер принимает только
   точные официальные general и Coding Plan URL и не допускает произвольный
   сетевой адрес. Идентификатор модели в ответе должен точно совпасть с
   запрошенным; маршрутизация поставщика на другую модель не считается
   эквивалентным именем и не принимается автоматически.

## 4. Инварианты контракта и происхождения

- Артефакт закрепляет версии контракта, методики и промта, поставщика, точный
  идентификатор модели, `throughEventSequence`, хэш канонического входного
  журнала и хэш точного структурированного результата.
- Каждый элемент блока фактов содержит хотя бы одну ссылку на существующее
  публичное событие из закреплённого журнала. Неизвестная ссылка отклоняет весь
  ответ; сервер не удаляет её и не исправляет частичный результат.
- Факты, интерпретации и вопросы остаются разными полями контракта и разными
  смысловыми секциями интерфейса. Модель не может повысить интерпретацию до
  подтверждённого факта.
- Запрос и ответ не меняют `stateVersion`, `throughEventSequence`, игровые
  события, счёт, доступность действий, расписание или квитанции.
- Идентичный request id закрепляет единственную попытку и результат. После
  перехода к внешнему вызову неизвестный исход сохраняется как терминальный
  fail-closed результат и не разрешает неявно повторить обращение.
- Подтверждение ведущего закрепляет точный хэш результата. Новая генерация
  создаёт новый артефакт; первая версия не вводит редактор свободного текста и
  историю правок.
- Любой вход и выход имеет отдельный ограниченный бюджет. Превышение приводит
  к явному отказу до внешнего вызова или сохранения результата, а не к
  усечению. Нормативная полная партия первого игрового среза обязана помещаться
  в бюджет.

## 5. Доступ, приватность и стоимость

- Создать, прочитать и подтвердить артефакт может только аутентифицированный
  ведущий соответствующей сессии. Публичность исходных игровых событий не
  делает ИИ-разбор общедоступным.
- Внешний запрос разрешён только сервером в явно настроенном проекте OpenAI с
  одобренным для среды профилем Modified Abuse Monitoring или Zero Data
  Retention. `store: false` обязательно, но само по себе не заменяет проверку
  профиля хранения данных. При отсутствии разрешённой конфигурации контур
  отказывает до отправки содержимого.
- Credential, заголовки поставщика и внутренние ошибки никогда не входят в
  клиентский контракт или сохранённое содержимое артефакта. Журналируется
  только ограниченная классификация отказа.
- Один запрос использует один закреплённый снимок модели, один максимальный
  бюджет выхода и ограниченную квоту на сессию. Изменение поставщика,
  разрешённого профиля данных или существенного профиля стоимости требует
  повторной архитектурной оценки.
- Психологические профили участников, кадровые рекомендации, скрытые оценки
  людей и обработка не предназначенных для публикации персональных заметок
  запрещены.
- Синтетическая проверка Z.AI не является новым production-поставщиком и не
  заменяет privacy/eval/model ворота OpenAI. Документированная неопределённость
  автоматического context caching дополнительно запрещает использовать в этом
  контуре реальные сессии, персональные данные и секреты.

## 6. Жизненный цикл и хранение

Отдельная запись проходит ограниченный жизненный цикл: принятая заявка,
начатый внешний вызов, завершённый черновик либо классифицированный отказ;
завершённый черновик может быть подтверждён ведущим. Переходы монотонны.
Успешный ответ и подтверждение сохраняются условным обновлением, чтобы
конкурентные запросы не создавали второй внешний вызов и не подтверждали уже
заменённые байты.

PostgreSQL является долговечным владельцем этого жизненного цикла. In-memory
реализация существует только как паритетный тестовый адаптер и не является
production-источником истины. Отдельная очередь, новый микросервис, векторная
база и provider conversation storage не вводятся; измеренная необходимость
асинхронного либо многошагового выполнения потребует нового решения.

## 7. Отклонённые варианты

- **Расширить переносимый журнал.** Отклонено: вероятностный вывод разрушил бы
  фактический read-only контракт ADR-103.
- **Использовать Agent Turn.** Отклонено: его назначение и транзакционная
  граница связаны с выбором изменяющего игрового намерения.
- **Хранить только в браузере.** Отклонено: теряются серверное происхождение,
  идемпотентность, аудит внешней передачи и проверяемое подтверждение.
- **Оставить mock-only.** Отклонено как конечный продукт: mock пригоден для
  контрактных тестов, но не даёт ведущему настоящего разбора.
- **Сразу добавить очередь, редактор, несколько поставщиков и иерархическое
  свёртывание.** Отклонено до измеримой необходимости: один ограниченный
  foreground-вызов сохраняет меньше компонентов и состояний отказа.

## 8. Последствия

- Игры могут публиковать собственную методику разбора через общий нейтральный
  контракт, не меняя режим исполнения и не добавляя предметные ветки в runtime.
- Ведущий получает проверяемый черновик, где можно перейти от утверждения к
  исходному событию и увидеть точное происхождение результата.
- Эксплуатация получает явные ворота приватности, стоимости и качества до
  настоящего внешнего трафика; без них возможность остаётся недоступной.
- PostgreSQL получает отдельный ограниченный класс данных с собственной
  политикой хранения. Удаление сессии и срок жизни производных артефактов должны
  оставаться согласованными в реализации и операционной политике.
- Будущие чат, редактирование, многошаговая обработка, второй поставщик или
  показ игрокам не следуют из этого решения автоматически.
