## 1. Понимание решения

Решение понято так: универсальный декларативный язык Mechanics получает две
обратно совместимые возможности.

Первая позволяет игровому плану отличить корректное временное отсутствие
маршрута от ошибки данных и явно выбрать дальнейшую ветвь. Вторая позволяет
считать и ранжировать фактический ограниченный набор объектов, полученный
серверной типизированной выборкой, а не только заранее перечисленные
идентификаторы.

Обе возможности остаются нейтральными. Поиск пути не знает причин закрытия
дорог, а подсчёт не знает ролей участников, формулы конкретной игры или смысла
победы.

## 2. Контекст

`graph.shortestPath` сейчас возвращает маршрут либо отклоняет всю транзакцию.
Аварийный исход нужен, когда маршрут обязателен, но недостаточен для условных
вычислений. В изменяемом графе корректные открытые узлы могут временно
оказаться в разных компонентах связности. Игровое действие в доступной части
графа не должно автоматически откатываться только потому, что вспомогательный
расчёт проверял достижимость другой точки.

`core.entities.score` и `core.ranking.stable` сейчас принимают статические
массивы идентификаторов. Это безопасно, но не покрывает сессии, где участники
или другие оцениваемые объекты создаются динамически, исключаются либо
фильтруются по текущему состоянию. Фиктивные слоты и клиентский подсчёт
нарушили бы общий серверный источник истины.

Общий язык уже имеет ограниченные `core.entities.select` и
`core.entities.order`. Их результат содержит доверенную коллекцию,
канонические идентификаторы и доказанную верхнюю границу, поэтому отдельный
универсальный язык запросов для этого решения не требуется.

## 3. Термины

- **Недостижимый маршрут** — отсутствие открытой последовательности рёбер
  между двумя существующими доступными узлами корректно объявленной сети.
- **Ошибка графа** — неизвестная сеть или объект, несовместимый тип,
  недоступный начальный или конечный узел либо нарушение модели.
- **Типизированная выборка** — результат `core.entities.select` или его
  проверенной производной `core.entities.order` с известной коллекцией и
  статической верхней границей.
- **Динамическая группа ранжирования** — фактические члены одной
  типизированной выборки, ранжируемые по уже вычисленной таблице результатов.

## 4. Неаварийный результат поиска пути

1. `graph.shortestPath` получает необязательное поле `onUnavailable` со
   значениями:
   - `fail` — прежнее поведение и значение по умолчанию;
   - `return-unreachable` — вернуть типизированный отрицательный результат,
     если открытого пути нет.
2. Успешный результат всегда содержит:
   - `reachable: true`;
   - канонические `edgeIds` и `nodeIds`;
   - `length`, равную числу рёбер.
3. В режиме `return-unreachable` отсутствие пути возвращает:
   - `reachable: false`;
   - пустые `edgeIds` и `nodeIds`;
   - `length: 0`.
4. Мягкий результат относится только к отсутствию связности между двумя
   корректными доступными узлами. Ошибки графа остаются ошибками при любой
   политике.
5. Проверяющий компилятор публикует `reachable` как обязательное логическое
   поле результата. Игровой план обязан проверить его перед интерпретацией
   пустого пути; нулевая длина сама по себе не означает недостижимость, потому
   что путь из узла в него же также имеет нулевую длину.
6. Алгоритм, канонический выбор при равенстве и статический бюджет обхода графа
   не меняются.

## 5. Подсчёт по динамической выборке

1. `core.entities.score` сохраняет существующую статическую форму
   `entities + entityIds`.
2. Альтернативная форма принимает `selection` — прямую ссылку на
   предшествующую типизированную выборку. Статическая и динамическая формы
   взаимоисключающие.
3. Для динамической формы `baseField` читается через объявленную модель поля
   коллекции. Поле обязано быть доступным серверу и иметь целочисленный тип,
   совместимый с существующей арифметикой результата.
4. `relatedSources` сохраняют прежний смысл. Получатели учитываются только
   тогда, когда их `ownerField` указывает на фактического члена выборки.
5. Условная выборка, которая могла не создать результат, не допускается как
   источник подсчёта. Условность должна находиться на самом шаге подсчёта либо
   быть выражена обычным предикатом селектора.
6. Runtime повторно проверяет происхождение результата, удаляет дублирование
   и обрабатывает идентификаторы в каноническом порядке.
7. Статическая стоимость и максимальный размер результата выводятся из
   `selector.cardinality.max`, сохранённого производной упорядочивания.

## 6. Ранжирование по динамическим группам

1. Каждая группа `core.ranking.stable` сохраняет статический вариант
   `entityIds` и получает взаимоисключающий вариант `selection`.
2. Динамическая группа допустима только для результата подсчёта, построенного
   из типизированной выборки той же коллекции.
3. Семантический проверяющий компилятор выводит максимальный размер группы из
   границы выборки и включает его в бюджет результата.
4. Runtime проверяет, что каждый член группы присутствует в таблице
   результатов; неизвестный, дублирующийся или неоценённый объект отклоняет
   транзакцию.
5. Порядок остаётся убывающим по результату с каноническим идентификатором как
   воспроизводимым техническим разрешением порядка отображения.
6. Равные результаты сохраняют общее место. Несколько объектов могут быть
   победителями одной группы.
7. Разные группы могут ссылаться на разные ограниченные подвыборки одной
   оценённой коллекции. Предметный смысл групп остаётся в пакете игры.

## 7. Ограничения и инварианты

- JSON Schema 2020-12 остаётся единственным источником истины формы шагов.
  Общие свойства объявляются на уровне объекта, а `oneOf` определяет только
  взаимоисключающие наборы обязательных полей.
- Значение по умолчанию `onUnavailable: fail` применяется исполнителем и не
  требует изменяющей входные данные настройки Ajv `useDefaults`.
- Клиент не может передать доверенную выборку, группу или исполняемый план.
- Динамические источники имеют известную коллекцию и верхнюю границу до
  публикации пакета.
- Информационный поток, аудитория и целостность выводятся из исходной
  коллекции и связанных источников так же строго, как для статической формы.
- Все вычисления входят в одну атомарную Mechanics-транзакцию и подчиняются
  общим бюджетам чтения, результата и аудита.
- Общий runtime не содержит ветвей по идентификатору игры, роли участника,
  типу транспорта или формуле результата.

## 8. Совместимость и версии

- Манифесты без новых полей сохраняют прежнюю форму и поведение.
- `onUnavailable` отсутствует — поиск пути продолжает завершаться ошибкой при
  отсутствии маршрута.
- Статические `core.entities.score` и `core.ranking.stable` продолжают
  работать без миграции.
- `cubica.graph` и `cubica.core` получают новые минорные версии и точные хеши
  исполняемого корпуса.
- Уже созданная поддерживаемая сессия продолжает ссылаться на прежние точные
  версии по ADR-086. Решение не возвращает и не замораживает удалённую
  архитектуру `deterministic.effects`.
- Новая сессия использует новые версии только после компиляции и публикации
  неизменяемого пакета с обновлённым `moduleLock`.

## 9. Отклонённые альтернативы

1. **Отдельная операция достижимости перед поиском пути.** Отклонено: два
   последовательных обхода одного графа дороже и создают два результата,
   которые игровому плану всё равно нужно связывать.
2. **Возвращать пустой путь без `reachable`.** Отклонено: путь из узла в него
   же законно пуст, поэтому результат неоднозначен.
3. **Смягчать ошибки неизвестного или закрытого узла.** Отклонено: это скрывает
   повреждение данных и обход правил доступности.
4. **Заранее создавать максимальное число фиктивных оцениваемых объектов.**
   Отклонено: служебные места загрязняют состояние, равенства и отчётность и
   повторяются в каждой игре.
5. **Считать или сортировать на клиенте.** Отклонено: официальный результат
   перестаёт быть серверным и воспроизводимым.
6. **Добавить предметную операцию финала отдельной игры.** Отклонено:
   предметная формула попадает в общий движок и создаёт будущую миграцию.
7. **Вводить новый универсальный язык запросов.** Отклонено для этой границы:
   существующая типизированная ограниченная выборка уже содержит необходимые
   происхождение, тип и бюджет.

## 10. Последствия

- Игровые планы могут безопасно ветвиться по временному отсутствию маршрута,
  не скрывая настоящие ошибки графа.
- Динамически созданные и отфильтрованные объекты могут участвовать в
  официальном серверном подсчёте и нескольких группах ранжирования.
- Схема, сгенерированные типы, semantic checker, runtime, каталог операций и
  точные блокировки модулей изменяются согласованно.
- Новые общие возможности доказываются нейтральными фикстурами; конкретная
  игра остаётся дополнительным потребителем, а не единственным определением
  контракта.
- Архитектура не получает новый сервис, хранилище, второй граф или отдельный
  интерпретатор. Это минимальное расширение уже существующих операций.
