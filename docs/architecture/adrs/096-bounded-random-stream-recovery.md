## 1. Понимание решения

Решение понято так: платформа сохраняет действующие зерно, счётчик,
идентификаторы алгоритмов и точную последовательность результатов
`xoshiro128**`, но больше не восстанавливает состояние повторением всех
исторических шагов.

Вместо этого runtime применяет ограниченный логарифмический переход к
сохранённому счётчику. Новая реализация получает новые точные версии и
контрольные хеши исполняемых модулей. Старый исполнитель не подменяется новым
под прежним хешем, а сохранённая сессия не переносится молча.

## 2. Контекст

Состояние каждого именованного случайного потока содержит зерно и
неотрицательный безопасный целочисленный счётчик. До этого runtime создавал
начальное состояние из зерна и выполнял `counter` переходов генератора.

Для короткой партии такой алгоритм практически незаметен. Для игры без
заданного числа ходов счётчик растёт вместе с партией:

- стоимость одного холодного восстановления растёт линейно;
- суммарная историческая работа последовательных восстановлений растёт
  квадратично;
- эта работа не выражена в бюджете Mechanics.

Проблема относится не к правилам одной игры. Колоды, случайное
упорядочивание, разрешение равенств и графовые алгоритмы используют общий
механизм именованных потоков.

## 3. Решение

1. Переход состояния `xoshiro128**` рассматривается как линейное
   преобразование 128 бит над полем из двух элементов: сложение является
   побитовым исключающим «или».
2. Runtime использует степени перехода для `1, 2, 4, 8, …` шагов.
3. Сохранённый счётчик раскладывается по степеням двойки. К начальному
   состоянию применяются только соответствующие степени перехода.
4. Для максимального безопасного целого JavaScript достаточно не более
   53 уровней. Цикл, число повторений которого равно сохранённому счётчику,
   запрещён.
5. Базовый переход, функция выдачи очередного 32-битного слова и устранение
   смещения при выборке диапазона не меняются.
6. Все 32-битные слова после побитовых операций нормализуются как беззнаковые.
   Счётчик принимается только как конечное неотрицательное безопасное целое.
7. Таблица степеней перехода не зависит от игры, сессии или зерна. Она
   формируется через статически ограниченную процедуру либо поставляется как
   воспроизводимый неизменяемый артефакт того же модуля.

Официальная документация семейства xoshiro подтверждает, что его линейная
рекуррентная структура допускает произвольные переходы по последовательности
через jump-полиномы. Конкретная внутренняя форма — полином или эквивалентная
матрица перехода — является деталью реализации при соблюдении инвариантов
этого решения.

## 4. Ограничение вычислений

- Восстановление ограничено числом уровней счётчика и размером состояния,
  а не значением счётчика.
- Для счётчика JavaScript допускается не более 53 уровней перехода.
- Модель стоимости заранее включает верхнюю границу применения переходов в
  `algorithmWork`.
- Стоимость списывается до выполнения случайного алгоритма. Нехватка бюджета
  отклоняет команду без изменения состояния, счётчиков, событий и квитанции.
- Подготовка неизменяемых степеней перехода имеет фиксированную верхнюю
  границу, не зависит от входной команды и не может вызвать накопительный
  рост работы по мере жизни сессии.
- Колоды, упорядочивание, выбор маршрута и другие потребители не реализуют
  собственное восстановление и не обходят общий учёт стоимости.

## 5. Воспроизводимость

Для любого допустимого `seed` и `counter` новое состояние обязано побитово
совпадать с состоянием после `counter` применений прежнего базового перехода.
Из этого следуют обязательные инварианты:

- уже опубликованные короткие контрольные последовательности не меняются;
- именованные потоки остаются независимыми;
- новости, грузы, разрешение равенств и маршруты получают прежние результаты;
- `advance(seed, A + B)` эквивалентен последовательному переходу на `A`, затем
  на `B`;
- идентификаторы `xoshiro128ss-v1` и `xoshiro128ss-streams-v1` сохраняются,
  потому что алгоритм последовательности и разбиение на потоки не меняются.

## 6. Совместимость сессий и версии

- Публичный формат состояния `seed + counter` не меняется.
- Новые сессии используют новые точные версии и хеши всех затронутых
  Mechanics-модулей.
- Старый `moduleVersion + artifactHash` никогда не указывает на новый код.
- Поддерживаемая старая сессия продолжает использовать закреплённый старый
  исполняемый корпус, если он сохранён согласно ADR-086.
- Предрелизная или тестовая сессия без доступного старого корпуса остаётся
  архивной и пересоздаётся на новом пакете. Это не замораживает развитие
  платформы и не возвращает удалённую архитектуру.
- Автоматическая перезапись `moduleLock` запрещена. Возможный журналируемый
  перенос доказанно эквивалентного состояния является отдельным будущим
  решением и не входит в этот срез.

## 7. Проверки

Реализация доказывается нейтральными проверками:

1. прежние опубликованные контрольные последовательности;
2. сравнение быстрого перехода с сохранённым линейным эталоном для множества
   небольших счётчиков и зерён;
3. композиция переходов для больших `A` и `B`;
4. границы около `Number.MAX_SAFE_INTEGER`;
5. независимость именованных потоков;
6. восстановление колоды, упорядочивания и графового выбора;
7. списание вычислительной стоимости до изменения случайности;
8. новые и прежние точные блокировки модулей без подмены хешей;
9. структурная проверка отсутствия цикла по сохранённому счётчику.

Измерение времени допустимо как диагностика, но не заменяет
детерминированную границу числа уровней и операций.

## 8. Отклонённые альтернативы

1. **Хранить четыре внутренних слова каждого потока.** Отклонено: меняет
   формат состояния, требует нового алгоритма потоков и миграции, хотя
   последовательность можно восстановить без этого.
2. **Хранить периодические контрольные точки.** Отклонено: усложняет
   долговечное состояние, очистку и проверку согласованности.
3. **Только учитывать линейную работу в бюджете.** Отклонено: достаточно
   длинная допустимая партия начнёт получать отказ вместо ограниченного
   восстановления.
4. **Ограничить число ходов.** Отклонено: противоречит подтверждённому
   продуктовому правилу ручного завершения.
5. **Кэшировать состояние только в памяти.** Отклонено: не помогает после
   рестарта и не закрывает постоянное хранение.
6. **Перейти на другой генератор с прямым доступом.** Отклонено: меняет
   будущие результаты и создаёт новую линию совместимости без необходимости.

## 9. Последствия

- Длительность партии больше не увеличивает скрытую стоимость холодного
  восстановления случайности.
- Воспроизводимость сохраняется без расширения публичного состояния.
- Общая модель бюджета охватывает исторический переход, а не только новые
  случайные слова.
- Реестр модулей, semantic checker, runtime и потребляющие игровые пакеты
  получают согласованные новые точные версии и хеши.
- После реализации и нейтральных доказательств `LEGACY-0067` закрыт.
- Игровые манифесты пересобираются на новых блокировках, но игровые правила и
  содержимое не меняются.
